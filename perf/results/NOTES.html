쉽게 보기 (3분 요약)

이 서비스가 하는 일: 아이가 이야기를 듣다가 마이크에 대고 말하면, 이야기 속 캐릭터가 대답합니다. 그 대답이 나오기까지 아이는 화면을 보며 기다립니다. 우리가 잰 것은 "아이가 얼마나 기다리는가"입니다.

아이가 한 번 말하면 뒤에서 벌어지는 일 (5단계):

단계하는 일걸린 시간
1. 받아쓰기아이 목소리를 글자로 바꿉니다0.8초
2. 이해하기AI가 아이 말의 뜻을 파악합니다2.6초
3. 대답 만들기AI가 캐릭터 대사를 씁니다1.7초
4. 저장하기대화 내용을 데이터베이스에 기록합니다0.04초
5. 목소리 만들기대사를 문장마다 음성으로 바꿉니다1.4초 x 문장 수

여기서 알게 된 것 세 가지:

  1. 느린 건 AI 두 번(2번, 3번)입니다. 전체의 96%. 데이터베이스는 0.04초라 아무 문제가 없습니다. 흔히 "DB를 최적화하자"고 하지만, 재 보니 여기서는 고칠 곳이 아니었습니다.
  2. 목소리 만들기(5번)가 숨어 있었습니다. 캐릭터가 세 문장으로 답하면 목소리 변환도 세 번 돕니다. 대답이 나온 뒤에 4~6초가 더 붙는데, 서버 기록에는 안 남아서 아무도 모르고 있었습니다.
  3. 말이 길면 더 오래 걸립니다. 아이가 길게 말하면 이해하는 데 오래 걸리고(짧게 말하면 3.2초, 길게 말하면 5.4초), 캐릭터 대답이 길면 대답 만들기와 목소리 만들기가 둘 다 길어집니다.

그래서 어떻게 고치면 되나: 더 비싼 AI를 쓰는 게 아니라, 캐릭터가 짧게 답하게 하고(대답 만들기와 목소리 만들기가 같이 줄어듦), 첫 문장 목소리가 나오면 바로 재생하면서 나머지를 만들면 됩니다. 지금은 세 문장을 다 만든 뒤에 재생을 시작합니다.

비유로 말하면: 식당에서 요리 3개를 주문했을 때, 셋 다 완성된 뒤 한꺼번에 내오는 것이 지금이고, 나오는 대로 하나씩 내오는 것이 개선안입니다. 손님이 먹기 시작하는 시각이 확 당겨집니다.

업계는 어떻게 하고 있나

우리가 겪은 문제들이 우리만의 문제인지 확인했습니다. 대부분 학계와 업계가 공식 보고한 문제였고, 해결 방향도 우리가 데이터로 찾은 것과 같았습니다.

1) 대화가 자연스러우려면 몇 초여야 하나

기준시간출처
사람끼리 대화할 때 대답 간격0~0.2초PNAS (10개 언어 연구)
GPT-4o 음성 모드 평균0.32초OpenAI 공식 발표
음성 AI 업계 목표치p50 0.5초 / p95 0.8초Vapi 엔지니어링 블로그
사용자가 봇 말을 끊기 시작하는 지점0.5초 초과업계 통설
우리 서비스 (현재)4.5초 + 목소리 1.4초이번 측정

업계 목표의 약 9배입니다. 다만 우리는 실시간 통화가 아니라 이야기 속 대화라 기준을 그대로 적용할 수는 없습니다. 그래도 줄일 여지가 크다는 사실은 분명합니다.

2) 업계가 쓰는 해결법 = 우리가 데이터로 찾은 방향

  • 스트리밍과 파이프라이닝: 다 만들고 내보내는 대신, 만들어지는 대로 이어 보냅니다. 업계가 재는 지표도 "전체 완성 시간"이 아니라 "첫 소리가 나오기까지의 시간"입니다 (LiveKit, Deepgram, Artificial Analysis).
  • 미리 시작하기: LiveKit은 아이 말이 끝나기 전에 AI 처리를 미리 시작하고, 말이 달라지면 버립니다. 토큰을 더 쓰는 대신 시간을 법니다.
  • 캐시: Character.AI는 캐시 적중률 95%로 초당 2만 건을 처리합니다. 방향이 "더 빠른 모델"이 아니라 "안 하는 일 늘리기"입니다.

3) 우리가 만난 STT 문제는 알려진 결함

발견업계/학계 보고
무음/잡음에 어휘 목록이 그대로 전사됨 (환각율 100%) Whisper가 무음 구간에서 프롬프트를 되돌려주는 현상은 공식 저장소에 보고된 알려진 결함
없는 말을 지어내 단어장을 오염시킴 FAccT 2024 연구: 전사본 약 1%에 오디오에 없는 문장, 그중 38%는 유해 내용. AP 조사: 공공회의 녹취 10건 중 8건에서 환각
아이 발음이 자주 틀리게 인식됨 아동 음성 인식 오류율은 성인의 2~5배. Whisper 그대로 쓰면 WER 13~25%, 아동 데이터로 학습하면 9%대 (Kid-Whisper, AIES 2024)

우리는 이 문제들을 세 겹으로 막았고, 그 효과를 실측했습니다: 에코 필터 (환각율 100% -> 0%), 자모 단위 교정, 실재 낱말 관문.

4) 다른 교육 서비스의 품질 관리

  • Khan Academy(Khanmigo): 레드팀 점검, 교육 밖 대화 차단, 위험 대화 시 보호자 자동 알림, 대화 내역 보호자 공개
  • Duolingo Max: OpenAI와 프롬프트/가드레일 협업, 정확성 이중 검증, A/B 테스트
  • ELSA Speak: 음소 단위 발음 채점, 전문가 평가와 93.9% 일치 주장
  • 음성 AI 테스트 도구(Coval, Hamming): 시뮬레이션 통화 수천 건을 CI에서 자동 실행. 자율주행 테스트 방법론을 음성 AI에 이식한 것

참고로 국내 키즈 AI 서비스 중 품질 검증 과정을 공개한 사례는 찾기 어려웠습니다. 측정으로 말하는 것 자체가 차별점이 됩니다.

5) 그래서 우리 로드맵

  1. 캐릭터 대답 길이 제한 -> 대답 만들기와 목소리 만들기가 함께 감소
  2. 목소리 파이프라이닝 -> 첫 문장부터 재생 시작
  3. 첫 소리까지 시간(TTFA)을 공식 지표로 채택 -> 업계와 같은 언어로 측정
  4. 실제 아이 목소리 평가셋 구축 -> 아동 인식 정확도를 숫자로 관리
  5. 대사 품질 골든셋 자동 검사 -> 프롬프트를 고칠 때마다 회귀 검증

핵심 관찰 (2026-08-17 측정 회차)

  • 턴의 96%는 두 번의 LLM 호출이다. 서버 턴 p50 4,469ms 중 분석 2,603ms + 대사 1,662ms. DB 구간(준비/판단/반영)은 합쳐 37ms - DB는 병목이 아니다.
  • 입력 길이가 분석을, 출력 길이가 대사를 움직인다. 발화 글자 수와 분석 시간의 상관 r=0.82, 응답 글자 수와 대사 시간의 상관 r=0.62 (현재 버전, 표본 39턴). 발화 버킷별 턴 p50: 짧은 3.2초 / 중간 4.5초 / 긴 5.4초.
  • 가장 큰 숨은 체감 구간은 TTS다. 완주 한 번에 TTS 호출 26~31회 (응답 문장 수만큼 순차), 미스 p50 1.4초, 긴 문장은 2.5초. 캐릭터가 3문장으로 답하면 턴 4.5초 뒤에 TTS 4~6초가 더 붙는다. 서버 캐시 적중 시 9ms로 실증됐지만 LLM 응답은 매번 새 문장이라 운영에서는 거의 못 맞는다.
  • 턴 응답 속도는 네 버전이 비슷하다. #68 -> 현재의 개선은 속도가 아니라 정확도/품질(STT 환각 차단, 유도 품질, 장면 흐름)이었다 - 정직하게 그렇게 발표하는 것이 맞다.
  • STT 지연은 음원 길이에 둔감하다. 2/5/10초 잡음 모두 p50 0.8초 안팎 - 짧은 발화에도 약 0.8초의 고정비가 든다.
  • 리포트는 완주 후 22~30초 걸리는 비동기 작업이다 (아이는 기다리지 않음). journey-v1(#68) 시점에는 90초 안에 준비되지 않았다 - 이후 버전에서 고쳐진 것도 개선사의 일부다.

개선 제안 (실측 근거)

  1. 캐릭터 응답 길이 상한. max_tokens가 어디에도 설정돼 있지 않다. 출력 길이가 대사 구간(r=0.62)과 TTS 총량(문장 수 비례)을 함께 키우므로, 프롬프트 규칙 + max_completion_tokens로 1~2문장을 강제하면 턴과 TTS 양쪽이 같이 줄어든다. 비용도 준다.
  2. TTS 파이프라이닝. 첫 문장 합성이 끝나면 바로 재생을 시작하고 나머지 문장은 재생 중에 병렬 합성(클라이언트 변경만으로 가능). 3문장 기준 체감 4~6초 -> 1.4초 수준.
  3. 분석+대사 호출 통합 검토. 두 LLM 호출은 직렬(대사가 분석 결과를 입력으로 씀)이라 병렬화가 불가능하다. 하나의 구조화 출력으로 합치면 왕복이 반으로 줄지만(이론상 턴 p50 4.5초 -> 2.6초 수준), 분석/대사 역할 분리라는 설계 의도와 프롬프트 복잡도 트레이드오프가 있어 A/B 실험 후 결정할 것.
  4. LLM 프롬프트 캐싱 검증. 분석 시스템 프롬프트는 2,278자 고정이라 벤더 프롬프트 캐시가 맞아야 정상인데 아무도 검증한 적이 없다. 응답의 캐시 토큰 지표를 로깅해 확인하고, 안 맞으면 프리픽스 고정 순서를 손본다.
  5. tts.vendor 조회 TTL 캐시. TTS 호출마다 app_settings SELECT가 나간다(회당 1건, 완주당 26~31건). 5~10초 TTL이면 전환 즉시성을 거의 잃지 않고 없앨 수 있다 - 다만 즉시 전환을 문서화한 의도가 있어 팀 합의 후.
  6. DB 캐시는 서두를 필요 없다. 장면 조회 N+1, 완주 트랜잭션의 아이템 해금 재계산 등은 코드상 낭비가 맞지만 실측 영향이 전부 50ms 미만이다. 체감 개선은 위 1~4에서 나온다 - 이것도 데이터가 주는 결론이다.
  7. STT 고정비 0.8초는 수용. 길이 둔감이라 자체 최적화 여지가 작다. 녹음 종료 즉시 업로드(이미 구현)를 유지하고, 개선은 벤더 스트리밍 지원 시 재검토.
