# 성능 재현 측정 하네스

핵심 기능의 "버전 1 -> N" 개선 흐름을 발표용 수치로 만드는 도구다. 과거 커밋을
버전별 격리 환경(전용 worktree + 전용 빈 DB)으로 띄우고, 같은 방법으로 재측정해
비교한다.

**정직성 원칙**: 여기서 나오는 수치는 전부 "현재 환경에서의 재현 측정"이다.
당시 운영 수치가 아니므로 발표에도 그렇게 표기한다. 당시에 잰 값은
`docs/트러블슈팅_*` 문서와 PR #92~#95 본문에 이미 있고, 그쪽이 1차 증거다.

## 트랙과 버전 지점

`versions.tsv`가 단일 진실이다. 트랙별 버전, 커밋, 포트, 패치 여부가 있다.

| 트랙 | 이야기 | 버전 수 | 주 지표 |
|---|---|---|---|
| turn | 턴 처리 중 DB 커넥션 점유로 무관 API까지 마비 -> 트랜잭션 분리 | 2 | 턴 부하 중 로그인/홈 p95, 성공률 |
| word | LLM 뜻 생성 도입 -> 사전 -> 20자 기준 -> 어절 기준 -> 예문 3종 | 5 | 오거절, 길이/어절 적합률, 지연 p95 |
| stt | STT 도입 -> 신뢰도 -> 힌트 에코 필터 -> 문장 프롬프트 -> 근접 교정 | 5 | 비발화 환각율, CER, 신뢰도, 지연 |
| journey | 이야기 시작부터 종료까지 전 구간 (AI 파이프라인 -> STT 정확도 -> 유도 프롬프트 -> 현재) | 4 | 구간별 p50/p95, 발화 길이 버킷별 턴 지연, TTS 호출 수 |

빈 DB에 그 버전 코드를 부팅하면 그 버전의 Flyway/시드가 스키마를 만든다.
최신 DB에 옛 코드를 붙이지 않는 이유이자, 버전 간 데이터가 공정해지는 방법이다.

## 준비물

- docker, k6(`brew install k6`), python3, 저장소 루트의 `.env`(OPENAI 키 포함)
- word/stt 트랙은 **실제 OpenAI 호출이 나간다**. 기본 설정 기준 트랙당
  호출 수십 건 수준이지만, 라운드를 늘리면 비용도 비례한다.

## 사용법

```bash
# 0) 한 번만: 버전 태그 생성 (로컬 태그)
perf/bin/tag-versions.sh

# 1) 버전 하나 띄우기 (첫 부팅은 gradle 배포판 다운로드로 수 분 가능)
perf/bin/up.sh perf/word-v1

# 2) 측정
perf/bin/run-word.sh perf/word-v1 --rounds 3

# 3) 내리기 (결과는 perf/results/에 남는다)
perf/bin/down.sh perf/word-v1

# 4) 전 버전 취합
python3 perf/bin/collect.py
```

트랙별 측정 명령:

```bash
perf/bin/run-turn.sh perf/turn-v1        # k6 - 턴 부하 중 무관 API 프로브
perf/bin/run-word.sh perf/word-v3 --rounds 3
perf/bin/run-stt.sh perf/stt-v2 --rounds 5
```

서버 포트가 버전마다 달라(8091~8102) 여러 버전을 동시에 띄워 번갈아 측정할 수
있다. **외부 AI가 끼는 트랙(word/stt)은 같은 시간대에 버전들을 번갈아 재는 것**이
벤더 혼잡도 변수를 상쇄하는 방법이다.

## 트랙별 상세

### turn - 느린 LLM 대역이 필요한 이유

문제가 발견/수정된 시점(PR #25 내부)에는 대화 LLM이 501 스텁이었다. 당시 팀의
회귀 테스트가 느린 테스트 대역으로 재현했듯, 하네스도 같은 기법을 쓴다:

- v1(57fb36f): analysis/character 스텁 클래스를 지연 대역으로 교체 (`patches/turn-v1/`)
- v2(0feceae): LlmClient 포트 뒤에 perf 프로파일 @Primary 대역 추가 (`patches/turn-v2/`)

지연은 `PERF_LLM_DELAY_MS`(기본 2000ms)로 두 버전에 똑같이 걸린다. up.sh가
패치 적용과 프로파일 활성화를 자동으로 한다.

읽는 법: v1은 턴 부하가 커지면 probe_login/probe_home p95가 지연 배수로 튀고
(커넥션 풀 고갈), v2는 턴만 느리고 프로브는 평평해야 한다.

### word - 품질과 지연을 한 번에

`eval/wordset.txt`의 11개 낱말(트러블슈팅 문서의 측정 낱말과 같은 성격, 사전에
없는 옛날 생활어)을 라운드마다 저장한다. 라운드 사이에 wordbook 표를 비워
중복 저장을 피한다. LLM 비결정성 때문에 라운드 3회 이상을 권한다.

- 오거절(422): 실재 낱말이므로 발생 전부가 잘못된 거절이다 - v3의 개선 대상
- 20자 초과: v3(#92)의 기준, 5~7어절: v4(#94)의 기준
- 예문 3종: v5에서 저장이 느려진 대신 얻은 것 - 지연 증가를 트레이드오프로 발표

### journey - 이야기 시작부터 종료까지, 구간별

아이 한 명이 이야기 하나를 완주하는 흐름을 클라이언트 관점에서 그대로 밟는다
(`eval/journey.py`). 서버가 재는 구간은 턴 하나뿐(TurnTimer 로그)이라 모든
HTTP 호출을 클라이언트에서 구간 이름표로 재고, 측정 후 server.log의
`턴 처리 sessionId=... 총 Nms (준비/분석/판단/대사/반영)` 줄을 파싱해 턴 행에
합류시킨다.

발화/응답 길이 의존이 핵심 설계다:

- 입력(아이 발화): short/medium/long 세 버킷을 턴마다 순환. 문장은 이야기
  맥락에 맞춰 고정했고, 전 버전에 같은 문장을 써야 비교가 성립한다.
- 출력(캐릭터 응답): 조절할 수 없으므로 관찰한다 - 응답 글자 수/문장 수를
  기록하고 서버의 대사 구간 ms와 상관을 본다. max_tokens가 없어 출력 길이가
  대사 구간을 지배한다는 가설의 검증 자리다.
- TTS: 클라이언트 실제 경로 그대로 응답 문장 수만큼 순차 호출한다. 이 구간은
  서버 로그에 전혀 안 잡히는 숨은 체감 구간이다. `eval/tts_eval.py`가 길이
  버킷 x 캐시(miss/hit) 곡선을 따로 잰다.
- STT: `noise_5s/10s.wav`로 음원 길이 vs 지연 스케일을 잰다.

리포트 준비(report_ready)는 비동기라 아이의 체감이 아니다 - 별도 지표로만
남긴다. 여정 비교는 코드와 이야기 콘텐츠(장면 구성, max_turns)가 함께 변한
총체의 비교라는 점을 발표에 명시할 것.

결과 시각화: `python3 perf/bin/report_html.py` -> `results/REPORT.html`
(외부 의존 없는 단일 파일, 인라인 SVG 차트).

### stt - 환각율이 핵심 지표

무음/백색잡음/순음(자동 생성, 고정 시드)은 발화가 아니다. 여기서 텍스트가
나오면 환각이고, 어휘 힌트 에코(v3가 잡은 문제)가 이 지표로 드러난다.
422 STT_EMPTY_TEXT는 잘 걸러낸 것이므로 성공으로 센다.

실제 아이 발화 정확도(CER)까지 재려면 `eval/samples/real/`에
"기대문장.wav"(파일명이 곧 정답)로 녹음을 넣는다. 같은 파일을 전 버전에
돌려야 비교가 성립한다.

## 공정성 체크리스트

- 같은 하드웨어에서, 측정 중 다른 무거운 작업 금지
- 워밍업 후 측정 (run-turn.sh는 30초 워밍업이 내장, eval은 라운드 1을 버려도 됨)
- 평균이 아니라 p50/p95와 표본 수를 보고
- 전체를 최소 2회 반복해 결과가 흔들리지 않는지 확인
- 버전 간 다른 것은 코드뿐인지 확인 (JVM/DB 버전, .env, 평가셋 동일)
- 옛 버전이 부르는 외부 모델명이 다르면 "모델 교체 포함"으로 명시
  (각 worktree의 application.yml에서 확인)

## 하네스 검증 실측 (2026-08-16, 구축 시 스모크)

하네스 자체가 동작하는지 각 트랙을 실제로 돌려 확인한 값이다. 본 측정의
미리보기이기도 하다 (표본이 작으니 발표에는 본 측정 값을 쓸 것).

- turn: 같은 조건(턴 16VU, LLM 지연 2000ms)에서
  v1 로그인 p95 3.70s / 홈 p95 3.75s, v2 로그인 p95 114ms / 홈 p95 41ms.
  같은 40초 동안 처리한 턴도 96 -> 144로 늘었다. 턴 VU가 풀(10)보다 적으면
  v1도 멀쩡해 보이니 주의 (6VU에서는 차이 없음을 실측).
- stt: v1(도입 시점)에서 무음/잡음/순음 전부가 어휘 힌트 목록
  ("며느리, 시아버지, 방귀, ...")을 그대로 돌려줬다 - 환각율 100%.
  트러블슈팅_STT_어휘_힌트_에코가 잡은 문제의 재현이다.
- word: v1에서 3낱말 스모크 기준 p95 2.8s, 20자 초과 1/3 검출.

## 주의

- 태그는 로컬이다. 공유하려면 `git push origin --tags 'refs/tags/perf/*'`
- worktree는 `~/git/goodquestion-perf/`(PERF_WORK_DIR로 변경 가능)에 생긴다
- 측정이 끝나면 `down.sh`로 내려야 DB 컨테이너와 gradle 데몬이 안 쌓인다
- 결과(perf/results/)는 git에 올리지 않는다 (.gitignore)
