# 캐시 전략

> **목적**: 어떤 데이터에 캐시를 걸었고, 어떤 데이터에는 일부러 걸지 않았는지,
> 그 판단 기준과 결과를 적는다. 다음에 누가 캐시를 추가하거나 빼려 할 때
> 같은 고민을 반복하지 않기 위한 문서다.

## 0. 요약

| 대상 | 방식 | 이유 |
| --- | --- | --- |
| scene_audio (사전 렌더 음성 메타) | 기동 시 전량 적재 불변 맵 | 전량 수십 행, 시드로만 변경, 장면 렌더마다 조회되던 것 |
| topics (토픽 마스터) | Caffeine + `@Cacheable` | 이야기 목록마다 전체 조회, 시드로만 변경 |
| items (아이템 마스터) | Caffeine + `@Cacheable` | 상점/행성/완주 세 경로가 각자 전체 조회, 시드로만 변경 |
| 장면 영상/이미지/음성 파일 | HTTP Cache-Control (max-age 1일) | 33MB 영상이 캐시 헤더 없이 반복 다운로드되던 것 |
| tts.vendor, 공지, 가이드 | **캐시 안 함** | 외부 프로세스(관리자 콘솔)가 쓰는 데이터 |
| 세션, 지갑, 해금 판정 | **캐시 안 함** | 아이마다 다르고 매 요청 달라지는 상태 |

## 1. 기존에 어땠나

### 1-1. 반복 조회

콘텐츠 마스터는 Flyway 시드로만 바뀌는 읽기 전용 데이터인데, 매 요청 DB에서 다시 읽고 있었다.

- **scene_audio**: 장면을 렌더하는 모든 경로(`장면 목록`, `이어하기`, `첫 대사`,
  `장면 전환`, `대화 종료`)가 건마다 조회했다. 특히 `GET /api/stories/{id}/scenes`는
  STORY 장면 수만큼 쿼리가 나갔다(시드 기준 장면 목록 1회에 scene_audio 5회).
  전형적인 N+1이고, 조회마다 읽기 전용 트랜잭션 진입 비용도 붙었다.
- **topics**: 이야기 목록을 열 때마다, 토픽 목록 API를 부를 때마다 전체를 다시 읽었다.
- **items**: 상점 목록, 행성의 다음 해금 안내, 완주 시 새 해금 계산 세 경로가
  각자 전체(45행)를 읽었다. 완주 한 번에 두 번 읽는 코드도 있었고,
  필터 람다 안에서 아이템마다 지갑을 다시 조회하는 지점도 있었다.

### 1-2. 정적 자산

장면 영상(mp4, 33MB)과 이미지, 사전 렌더 음성이 Cache-Control 없이 나갔다.
헤더가 없으면 브라우저가 휴리스틱 캐시에 기대는데, 그 판단은 브라우저마다 다르고
같은 영상을 장면마다 다시 받는 쪽으로 기울기 쉽다.

### 1-3. 이미 있던 캐시

TTS 클라이언트 3개(OpenAI/Gemini/Chirp)가 각자 ConcurrentHashMap으로 합성 결과를
캐시하고 있었다. 이 부분은 이번 작업 범위 밖이며, 한계(상한 도달 시 전체 삭제,
라우터 구조상 2벌은 항상 유휴)는 6절에 적었다.

## 2. 무엇을 고려했나

### 2-1. 첫 질문: 이 데이터는 누가, 언제 바꾸는가

캐시의 어려움은 넣기가 아니라 **무효화**다. 그래서 대상마다 쓰기 경로부터 전수 확인했다
(리포지토리 save/delete 호출처 grep, 2026-08-18).

| 분류 | 데이터 | 판단 |
| --- | --- | --- |
| 이 서버에 쓰기 경로 없음, 시드로만 변경 | stories, story_scenes, scene_audio, topics, items, characters | 무효화가 필요 없다. 재배포 = 재시작 = 재적재 |
| 외부 프로세스(관리자 콘솔)가 씀 | app_settings(tts.vendor), notices, guides | 이 프로세스 안에서 무효화 신호를 만들 수 없다. TTL 말곤 수단이 없으므로 걸지 않는다 |
| 아이별, 매 요청 변화 | 세션, 지갑, 해금 판정 | 캐시 금지. 해금을 저장하지 않고 매번 계산하는 이유는 ItemUnlockPolicy 주석 참고 |

첫 번째 분류만 캐시 대상이다. 무효화 코드가 0줄이라는 것이 이 전략의 핵심이고,
그 전제(시드로만 변경)가 깨지는 순간 TTL을 달거나 캐시를 빼야 한다는 경계를
CacheConfig와 SceneAudioCache 주석에 남겼다.

### 2-2. 두 번째 질문: 어떤 캐시 기술을 쓰는가

같은 "읽기 전용 마스터"라도 크기와 접근 형태가 달라 방식을 갈랐다.
기능마다 다른 캐시를 쓴 이유가 여기 있다. 세 후보를 놓고 비교했다.

| | 자바 자료구조 (불변 맵) | Caffeine | Redis |
| --- | --- | --- | --- |
| 위치 | 앱 힙 | 앱 힙 | 별도 프로세스 |
| 읽기 비용 | 약 10~20ns (맵 조회) | 약 40~80ns (조회 + 접근 빈도 기록) | 약 0.2~1ms (직렬화 + 네트워크) |
| 축출 | 없음 (전량 상주) | 크기/무게 기준, W-TinyLFU | 메모리 정책 기반 |
| 만료 | 없음 | TTL 지원 | TTL 지원 |
| 미스 경로 | 없음 (항상 적중) | 있음 (첫 요청, 축출 후) | 있음 |
| 인스턴스 공유 | 안 됨 | 안 됨 | 됨 |
| 재기동 생존 | 안 됨 | 안 됨 | 됨 |
| 추가 인프라 | 없음 | 의존성 1개 | 서버, 환경변수, 장애 대응 |
| 새 실패 모드 | 없음 | 없음 | 있음 (다운 시 폴백 필요) |

**속도 차이는 판단 근거가 아니었다.** 셋 다 DB 왕복(1~3ms)을 없애는 것이 본질이고,
그다음 차이는 나노초 단위라 체감되지 않는다. Redis만 밀리초대지만 그조차 DB보다
빠르다. 그래서 속도가 아니라 **데이터의 성질과 운영 비용**으로 갈랐다.

#### scene_audio -> 자바 불변 맵

- 공용 행이 전량 13행이다. **전부 들 수 있으면 축출 정책이 필요 없다.**
  Caffeine을 써도 `maximumSize`가 영원히 발동하지 않고, TTL을 걸면 낡지도 않은
  값을 주기적으로 버렸다 다시 읽는다. 기능이 안 쓰이는 라이브러리를 넣는 셈이다.
- 미스 경로가 아예 없다는 것이 이 선택의 실질적 이득이다. Caffeine이었다면
  첫 요청들이 DB를 타고, 그 요청만 느리다. 전량 적재는 모든 요청이 같은 속도다.
- 소비 형태도 맞았다. 리졸버가 "장면의 후보 목록을 받아 해시로 거른다"라서
  장면 ID -> 목록 맵이 그대로 필요한 모양이었다. `@Cacheable`로 감싸면
  오히려 한 겹이 는다.
- 대신 전제가 좁다. **전량이 메모리에 들어가야 한다.** 아이별 음성(child_id)이
  생기면 아이 수에 비례해 자라므로 이 방식은 그때 깨진다. 그래서 공용 행만
  담고, 그 경계를 주석에 적었다.

#### topics, items -> Caffeine

- 소비 형태가 "목록 통째로 반환"이라 서비스 메서드에 `@Cacheable` 한 줄이
  그대로 맞는다. 전량 적재 홀더를 또 만들면 같은 일을 하는 코드가 는다.
- items는 45행이고 이야기가 늘면 함께 는다. 지금은 전량 적재도 가능하지만,
  **상한을 둘 수 있는 쪽이 나중에 안전하다.** `maximumSize`는 정책이 아니라
  나중에 누가 키 있는 메서드를 같은 캐시에 얹었을 때의 안전판이다.
- TTL은 두지 않았다. 시드로만 바뀌므로 재배포가 곧 무효화다.
- 선언적이라 캐시 여부가 코드에 드러난다. 홀더 클래스는 읽어 봐야 안다.

#### Redis를 쓰지 않은 이유

- **공유와 생존이라는 Redis의 두 장점이 지금 값이 0이다.** 배포는 Railway
  단일 인스턴스이고(deploy-railway.md), 캐시 대상은 재기동 시 다시 읽으면
  그만인 수십 행짜리 마스터다.
- 반면 단점은 즉시 발생한다. 서비스 하나가 늘고, 환경변수가 늘고, **Redis가
  죽었을 때의 폴백 코드**가 필요하다. 이 코드베이스는 외부 호출 실패에 대한
  애플리케이션 폴백이 아직 없는 상태라(안정적인_서비스_만들기.md), 캐시 하나
  때문에 새 장애 지점을 만드는 것은 순서가 뒤바뀐 일이다.
- 값의 크기도 안 맞는다. 오디오를 Redis에 넣는다면 40~176KB짜리 base64를
  매번 네트워크로 나르게 되는데, 이는 Redis가 잘하는 일이 아니다.
- **다음 중 하나라도 성립하면 Redis가 답이 된다**: 인스턴스를 둘 이상으로
  늘릴 때, 오디오를 오브젝트 스토리지로 옮겨 캐시 값이 짧은 URL이 될 때,
  또는 멱등키나 레이트 리밋처럼 Redis를 쓸 다른 이유가 생길 때.

#### 영상과 이미지 바이트 -> HTTP 캐시

33MB를 앱 힙에 올리는 것은 캐시가 아니라 낭비다. 바이트는 브라우저와 중간 캐시가
들게 하는 것이 맞고, 서버는 헤더만 단다. 파일명에 버전이 없어 무한 캐시는 걸 수
없으므로 max-age를 하루로 제한했다(배포 다음 날이면 확실히 새 파일).

#### 정리

| 기능 | 선택 | 결정적 이유 |
| --- | --- | --- |
| scene_audio | 불변 맵 | 전량 13행이라 축출이 무의미. 미스 경로 없음 |
| topics, items | Caffeine | 목록 반환 형태에 `@Cacheable`이 맞음. 증가 대비 상한 |
| 영상/이미지 바이트 | HTTP 캐시 | 33MB를 앱 힙에 올리는 것은 캐시가 아니라 낭비 |
| tts.vendor, 공지 | 캐시 안 함 | 외부 프로세스가 씀. 관측 가능성이 캐시 이득보다 중요 |

### 2-3. 세 번째 질문: 캐시에 무엇을 담는가

**JPA 엔티티는 캐시에 담지 않는다.** 엔티티가 영속성 컨텍스트 밖에서 여러 요청에
공유되면 LAZY 연관은 세션이 닫힌 뒤 터지고, 누가 실수로 값을 바꾸면 모든 요청에
번진다. 그래서 캐시마다 값 객체를 따로 만들었다.

- scene_audio: `SceneAudioView` (URL, 원문 해시, 문장별 실측 시각)
- items: `ItemView` (표시 필드 + 해금 이야기의 제목/이미지를 적재 시점에 풀어 둠)
- topics: 기존 응답 DTO(`TopicResponse`)를 그대로 캐시

`ItemView`에는 해금 여부가 없다. 목록은 모든 아이에게 같고 해금은 아이마다 다르다.
이 경계가 무너지면 한 아이의 해금 상태가 캐시를 타고 다른 아이에게 보인다.
ContentCacheTest가 뷰에 아이별 필드가 없음을 구조적으로 고정한다.

## 3. 어떻게 개선했나

### 3-1. scene_audio 전량 적재 (`SceneAudioCache`)

- `ApplicationReadyEvent`에서 공용 음성(child_id null) 전량을 읽어
  장면 ID -> `SceneAudioView` 목록 불변 맵으로 적재.
- `SceneAudioResolver`는 DB 대신 이 맵을 본다. **해시 대조는 리졸버에 그대로
  남긴다.** 캐시는 "이 장면에 어떤 음성이 있는가"까지만 알고, "지금 이 문장에 써도
  되는가"는 매번 판정해야 한다. 이 대조가 대사를 고친 경우와 아이 이름이 치환된
  문장을 걸러 실시간 합성으로 흘려보내는 장치라, 캐시가 매칭까지 삼키면
  화면의 새 문장에 스피커의 옛 문장이 나가는 사고가 생긴다.
- 적재 전(기동 직후의 짧은 구간)에는 빈 결과가 나간다. 사전 렌더 없는 장면과 같은
  경로라 클라이언트가 평소처럼 /api/tts로 합성한다. 틀린 답이 아니라 느린 답이다.
- 아이별 음성(child_id 있는 행)은 담지 않는다. 지금은 만드는 곳이 없고, 생기면
  아이 수에 비례해 자라 전량 적재 전제가 깨지므로 별도 경로여야 한다.
- 호출자가 없던 `urlFor()`와 장면 단위 리포지토리 메서드 2개를 제거했다.

### 3-2. topics, items Caffeine 캐시

- `TopicService.getTopics()`: 목록 API와 이야기 목록의 필터 칩이 같은 캐시를 쓴다.
  리포지토리를 직접 부르던 컨트롤러가 서비스를 거치도록 바꿨다.
- `ItemCatalog.activeItems()`: 상점, 행성, 완주 계산 세 경로가 같은 캐시를 쓴다.
  해금 이야기(제목/이미지)를 페치 조인으로 함께 읽어 뷰에 풀어 두므로, 목록을
  낼 때마다 이야기를 다시 읽지 않는다. 이 메서드에는 `@Transactional`을 걸지
  않았다(이유는 4-3절 (1)).
- `ItemUnlockPolicy`는 뷰 기반 판정이 원본이고, 단건 구매 검증의 엔티티 경로는
  뷰로 변환해 위임한다. 판정 규칙이 두 벌이면 한쪽만 고쳐져 "목록에선 열렸는데
  구매는 거절"로 갈라지기 때문이다.
- 곁다리로 완주 경로의 중복을 정리했다: items 전체 2회 조회 -> 캐시 1회,
  필터 안 아이템마다 지갑 조회 -> 지급 후 1회.

### 3-3. 정적 자산 HTTP 캐시

- `spring.web.resources.cache.cachecontrol.max-age: 1d` 추가.
- 테스트로 고정: 영상과 이미지에 헤더가 실제로 실리는지, 그리고 영상이 Range
  요청에 206으로 답하는지(안 되면 재생 위치를 옮길 때마다 처음부터 다시 받는데,
  큰 파일에서만 드러나 이미지 테스트로는 안 잡힌다).

## 4. 결과

### 4-1. 쿼리 수 (시드 기준, 캐시 적재 후)

| 경로 | 전 | 후 |
| --- | --- | --- |
| GET /stories/{id}/scenes (장면 9개) | scene_audio 5회 + 목록 1회 | 목록 1회 |
| GET /sessions/{id}/resume | scene_audio 2회 포함 | scene_audio 0회 |
| 대화 장면 종료(CLOSING) | scene_audio 1회 | 0회 |
| GET /stories (이야기 목록) | topics 전체 1회 | 0회 |
| GET /shop/items | items 전체 1회 + 해금 이야기 LAZY 조회 | 0회 |
| 행성 조회의 다음 해금 안내 | items 전체 1회 | 0회 |
| 완주(retelling) 1회 | items 전체 2회 + 아이템마다 지갑 조회 | items 0회 + 지갑 1회 |

수치로 크게 자랑할 개선은 아니다. 각 쿼리는 원래 밀리초 단위였고, 이 서비스의
응답 시간은 LLM 대기가 지배한다. 의미는 다른 데 있다: 목록성 경로(홈, 이야기 선택,
상점)는 LLM이 없어서 DB 왕복이 그대로 체감이 되는 곳이고, 동시 사용자가 늘 때
커넥션 풀(10개)을 두고 경쟁하는 쿼리 수가 줄어든다.

### 4-2. 테스트로 고정한 것

- `SceneAudioCacheTest` (5건): 시드 13건 적재, 해시 일치 시 매칭, 한 글자만 달라도
  걸러짐, 장면 목록의 STORY 장면마다 음성 URL, 없는 장면은 빈 목록
- `ContentCacheTest` (4건): topics/items 반복 호출 시 동일 참조(캐시 증명),
  해금 이야기 제목이 적재 시점에 풀려 있음, ItemView에 아이별 필드 없음
- `StoryAssetServingTest` (2건 추가): Cache-Control 헤더, 영상 Range 206
- 전체 스위트 통과 (기존 회귀 없음)

### 4-3. 구현 중 부딪힌 것들

캐시는 넣는 것보다 "넣었더니 다른 게 조용히 망가지는" 쪽이 어렵다.
작업하며 실제로 걸린 다섯 가지를 남긴다.

#### (1) `@Cacheable`과 `@Transactional`을 한 메서드에 걸면 순서에 결과가 딸려간다

**증상이 될 뻔한 것**: `ItemCatalog.activeItems()`에 처음에는 둘을 같이 걸었다.
해금 이야기가 LAZY라 제목을 읽으려면 트랜잭션이 필요했기 때문이다.

**문제**: 두 애노테이션은 각각 별도 어드바이저이고 기본 순서가 같다
(둘 다 `LOWEST_PRECEDENCE`). 어느 쪽이 바깥인지에 따라 동작이 갈린다.
캐시가 바깥이면 적중한 요청은 트랜잭션을 열지 않는다. 트랜잭션이 바깥이면
**캐시가 맞아도 매 요청 커넥션을 얻었다 반납한다.** 캐시를 넣은 이유의
절반(커넥션 점유 감소)이 사라지는데, 응답은 정상이라 눈치채기 어렵다.

**해결**: 순서에 기대는 대신 트랜잭션이 필요할 이유를 없앴다. 리포지토리에
페치 조인을 걸어 해금 이야기를 함께 읽게 하고(`findAllActiveWithUnlockStory`),
`@Transactional`을 뗐다. 조회 자체는 Spring Data 리포지토리가 자기 트랜잭션에서
처리하므로 문제없고, 이제 캐시가 맞으면 DB도 트랜잭션도 건드리지 않는다.
덤으로 STORY_COMPLETE 아이템 4건에 나가던 이야기 조회도 사라졌다.

**교훈**: 캐시 메서드는 트랜잭션이 필요 없게 만드는 것이 가장 확실하다.
애노테이션 순서를 명시(`@EnableCaching(order=...)`)해서 푸는 방법도 있지만,
전역 설정이라 다른 캐시까지 영향을 받고 읽는 사람이 알기 어렵다.

#### (2) 캐시가 기존 안전장치를 삼킬 뻔했다

**맥락**: 사전 렌더 음성은 슬롯이 아니라 **원문 SHA-256 해시**로 고른다.
대사를 고쳤을 때 화면엔 새 문장, 스피커엔 옛 문장이 나가는 상태를 막는 장치이고,
아이 이름이 치환된 문장("민준아, ...")이 공용 음성과 어긋나 자동으로 걸러지는
것도 같은 원리다.

**위험**: 캐시를 "장면 ID + 문장 -> 음성"으로 잡으면 편하다. 하지만 그러면
해시 대조가 캐시 안으로 들어가고, 대사가 바뀌었을 때 캐시가 옛 판정을 그대로
재생한다. **틀린 음성이 나가는데 아무도 모른다.**

**해결**: 캐시는 "이 장면에 어떤 음성이 있는가"까지만 안다. 지금 이 문장에 써도
되는지는 리졸버가 매번 해시로 판정한다. 캐시가 후보를 좁혀 줄 뿐 판정은 대신하지
않는다는 경계를 코드 주석과 테스트로 못박았다
(`문장이_달라지면_해시가_어긋나_잡히지_않는다`).

#### (3) 아이별 상태가 캐시를 타고 샐 수 있다

**위험**: items 캐시를 만들 때 상점 응답(`ShopItemResponse`)을 통째로 캐시하면
쿼리가 더 줄어든다. 그런데 그 응답에는 `unlocked`, `purchasable`, `shortfall`처럼
**아이마다 다른 값**이 들어 있다. 캐시하면 한 아이의 해금 상태가 다른 아이에게
그대로 보인다. 개인정보 문제이자 명백한 버그다.

**해결**: 캐시에 담는 `ItemView`에는 아이별 필드를 두지 않았다. 목록(모든 아이에게
같음)만 캐시하고, 해금 판정은 매 요청 계산한다. 리뷰로만 지키면 언젠가 새는 규칙이라
테스트가 구조적으로 고정한다 - `ItemView`의 레코드 컴포넌트에 `unlocked`나 `child`가
들어간 이름이 생기면 실패한다(`아이템_뷰에는_아이별_상태가_없다`).

#### (4) 판정 로직이 두 벌이 될 뻔했다

**맥락**: 해금 판정(`ItemUnlockPolicy`)이 엔티티를 받고 있었는데, 캐시가 뷰를
쓰면서 뷰용 판정이 필요해졌다.

**위험**: 그대로 뷰용 메서드를 하나 더 만들면 같은 규칙이 두 곳에 산다. 나중에
해금 조건을 고칠 때 한쪽만 고쳐지면 **목록에선 열렸는데 구매는 거절되는** 상태가
된다. 사용자에겐 이유를 알 수 없는 오류다.

**해결**: 뷰 기반 판정을 원본으로 두고, 엔티티 경로(단건 구매 검증)는 뷰로 변환해
위임한다. 규칙은 한 곳에만 있다.

#### (5) 테스트에서 캐시가 살아남는다

**맥락**: 스프링 컨텍스트는 테스트 클래스 간에 재사용된다. 캐시도 함께 살아남는다.

**현재 상태**: 문제없다. topics/items를 런타임에 삽입하는 테스트가 없어서
(전수 확인, 2026-08-18) 캐시가 낡을 일이 없다.

**주의**: 앞으로 이 마스터에 행을 넣고 목록을 확인하는 테스트를 쓰면, 앞선 테스트가
채운 캐시 때문에 새 행이 안 보인다. 그때는 해당 테스트에서 캐시를 비우거나
(`CacheManager.getCache(name).clear()`) 캐시를 끈 프로파일을 써야 한다.
증상이 "테스트를 단독으로 돌리면 통과하는데 전체로 돌리면 실패"로 나타나
원인을 찾기 어려운 유형이다.

**캐시가 걸렸는지 확인하는 법**: 반복 호출의 반환값이 **같은 참조**인지 본다
(`isSameAs`). 캐시가 없으면 매번 새 리스트가 만들어져 참조가 다르다.
값 비교(`isEqualTo`)로는 캐시 여부를 알 수 없다.

## 5. 일부러 하지 않은 것

- **tts.vendor 캐시**: 매 합성마다 PK 조회 1회가 나가지만 걸지 않았다.
  RoutingTtsClient 주석의 판단(합성은 턴당 한 번 수준이라 PK 조회는 값싸고,
  캐시를 두면 벤더 전환이 언제 먹었는지 흐려진다)이 옳다. 관리자 콘솔이 쓰는
  값이라 TTL 말고는 무효화 수단이 없다는 점도 같다.
- **공지/가이드 캐시**: 같은 이유(외부 콘솔이 씀). 공지는 조회수 UPDATE까지 있다.
- **세션/지갑/해금 캐시**: 아이별 상태는 캐시 금지가 원칙이다.
- **오디오/영상 바이트의 서버 메모리 캐시**: 바이트는 HTTP 캐시의 일이다.

## 6. 남은 것

- **TTS 합성 캐시 통합**: 벤더 클라이언트 3개에 같은 캐시 코드가 복사돼 있고,
  라우터 구조상 한 시점에 한 벌만 일한다. 라우터 위 데코레이터 하나로 합치고,
  개수 상한(512) 대신 바이트 예산으로 바꾸는 것이 다음 작업이다. 사전 렌더가
  연결된 지금은 이 캐시에 남는 것이 LLM 생성 대사(재사용 거의 없음)와 아이 이름
  치환 대사뿐이라, 캐시 대상 자체를 좁히는 것까지 포함해야 한다.
- **정적 자산의 스토리지/CDN 이관**: 자산 38MB가 jar에 들어가 jar가 91MB다.
  오브젝트 스토리지로 옮기면 배포가 가벼워지고 Cache-Control에 public을 붙여
  CDN까지 활용할 수 있다. 스토리지 선정이 팀 결정 사항이라 보류.
- **아이별 사전 렌더**: scene_audio.child_id 컬럼은 있으나 쓰는 곳이 없다.
  아이 이름 치환 대사를 아이별로 미리 렌더하면 TTS 캐시가 필요한 마지막 경우가
  사라진다. 스토리지 결정과 함께 가야 한다.

## 7. 발표용 정리

**견고한 서비스를 만들기 위한 요소는 무엇인가.**
캐시에서는 "무엇을 캐시하느냐"보다 "무엇을 캐시하지 않느냐"가 견고함을 가른다.
우리는 데이터를 세 부류로 나눴다. 시드로만 바뀌는 것(캐시, 무효화 코드 0줄),
다른 프로세스가 바꾸는 것(캐시 안 함), 아이마다 다른 것(캐시 금지). 이 분류가
있으면 무효화 버그라는 캐시의 최대 리스크가 설계 단계에서 사라진다. 그리고
캐시 종류도 데이터 성질에 맞춰 갈랐다. 수십 행짜리 불변 데이터에는 축출형
캐시(Caffeine)가 아니라 전량 적재가 맞고, 대용량 바이트에는 서버 메모리가 아니라
HTTP 캐시가 맞다.

**기능마다 캐시가 다른 이유는 무엇인가.**
데이터 성질이 다르기 때문이다. 속도로 고른 것이 아니다. 셋 다 DB 왕복을 없애는
것이 본질이고 그 뒤 차이는 나노초라 체감되지 않는다. scene_audio는 전량 13행이라
축출 정책이 영원히 발동하지 않으므로 라이브러리 대신 불변 맵을 썼고, 그 대가로
"전량이 메모리에 들어간다"는 좁은 전제를 안았다. topics와 items는 늘어날 수 있고
소비 형태가 목록 반환이라 `@Cacheable`이 그대로 맞아 Caffeine을 썼다. 33MB 영상은
앱 힙에 올릴 대상이 아니라 HTTP 캐시의 일이다. Redis는 공유와 재기동 생존이라는
장점이 단일 인스턴스에서 값이 0인 반면, 새 장애 지점과 폴백 코드라는 비용은 즉시
발생해서 넣지 않았다. 인스턴스를 늘리거나 오디오를 스토리지로 옮기면 그때 답이 바뀐다.

**구현할 때 어떤 어려움이 있었나.** (자세한 내용은 4-3절)
첫째, `@Cacheable`과 `@Transactional`을 한 메서드에 걸면 어드바이저 순서에 결과가
딸려간다. 트랜잭션이 바깥이면 캐시가 맞아도 매번 커넥션을 얻는데, 응답은 정상이라
눈치채기 어렵다. 순서에 기대는 대신 페치 조인으로 트랜잭션이 필요할 이유를 없앴다.
둘째, 캐시가 기존 안전장치를 삼킬 뻔했다. 사전 렌더 음성은 원문 해시가 일치할 때만
쓰는데(대사 수정과 이름 치환 감지), 캐시가 매칭까지 대신하면 틀린 음성이 나가는데
아무도 모른다. 캐시는 후보까지만 알고 판정은 매번 하도록 경계를 그었다.
셋째, 아이별 상태가 캐시를 타고 샐 수 있었다. 상점 응답을 통째로 캐시하면 편하지만
해금 여부가 아이마다 다르다. 목록만 캐시하고 판정은 매번 계산하며, 이 경계를
리뷰가 아니라 테스트가 지키게 했다.
넷째, 해금 판정을 뷰 기반으로 옮기면서 규칙이 두 벌이 될 뻔했다. 한쪽만 고쳐지면
목록과 구매가 갈라지므로, 엔티티 경로가 뷰로 변환해 위임하게 했다.

**해결 결과는 무엇인가.**
장면 목록의 N+1(장면당 1쿼리)이 구조적으로 사라졌고, 목록성 경로 전반에서 매 요청
나가던 마스터 조회가 0이 됐다. 33MB 영상의 반복 다운로드를 캐시 헤더로 막았다.
전부 테스트로 고정했다(캐시 동일 참조 증명, 해시 걸러짐, 헤더와 Range 응답).
그리고 하지 않은 결정도 근거와 함께 문서에 남겼다. 벤더 전환 설정처럼 관측
가능성이 캐시 이득보다 중요한 곳은 그대로 뒀다.
