# 발화 분석 및 진행 판단 연동 기준

# 굿퀘스천

## 발화 분석 및 진행 판단 연동 기준

---

## 1. 요약

아이의 발화가 입력되면 다음 순서로 처리합니다.

1. **발화 분석 모델**이 이번 발화에 포함된 사고 요소를 태깅합니다.
2. **서버 후처리 모듈**이 분석 결과의 근거와 형식을 검증합니다.
3. **진행 규칙 엔진**이 누적 상태를 바탕으로 일반 반응, 유도, 종료 중 하나를 결정합니다.
4. **캐릭터 응답 모델**이 결정된 진행 방식에 맞춰 대사를 생성합니다.

---

## 2. 전체 처리 구조

```
아이 최신 발화
    │
    ▼
① 발화 분석 모듈
    · 아이 최신 발화의 의도 분석
    · 사고 요소 탐지
    · 발화 유효성 판정
    │
    ▼
② 서버 후처리 모듈
    · 원문 근거 검증
    · 중복 요소 정리
    · 과도하거나 약한 탐지 보정
    │
    ▼
③ 진행 판단 모듈
    · 현재까지 누적된 사고 요소 확인
    · 부족한 필수 요소 확인
    · 대화 정체 및 저정보 발화 확인
    · NORMAL / GUIDED / CLOSING 결정
    │
    ▼
④ 유도 정보 구성
    · 필요한 경우 유도 대상 요소 선택
    · 요소에 대응하는 캐릭터의 걱정 정보 전달
    │
    ▼
⑤ 캐릭터 응답
    · NORMAL 또는 GUIDED: 캐릭터 모델 호출
    · CLOSING: 장면별 종료 처리
```

| 단계 | 담당 모듈 | LLM 사용 | 주요 역할 |
| --- | --- | --- | --- |
| 발화 분석 | 분석 모델 | 사용 | 사고 요소와 원문 근거 추출 |
| 후처리 | 서버 코드 | 미사용 | 근거·중복·약한 탐지 검증 |
| 진행 판단 | 규칙 엔진 | 미사용 | 모드, 종료 여부, 유도 대상 결정 |
| 캐릭터 응답 | 캐릭터 모델 | 사용 | 캐릭터 대사 생성 |
| 장면 종료 | 서버 또는 콘텐츠 설정 | 미사용 | 고정된 종료 처리 실행 |

---

## 3. 모듈별 책임 분리

대화 구조는 분석, 진행, 표현을 분리하여 진행하고 있습니다.

### 3.1 발화 분석 모듈

발화 분석 모듈은 다음 정보만 판단합니다.

- 아이가 이번 발화에서 무엇을 하려는지
- 어떤 사고 요소가 직접 드러났는지
- 해당 사고 요소의 원문 근거가 무엇인지
- 발화가 정상적인 정보 발화인지, 짧거나 불명확한 발화인지

### 3.2 진행 판단 모듈

진행 판단 모듈은 분석 결과와 누적 대화 상태를 이용하여 다음을 결정합니다.

- 현재 대화를 일반적으로 이어갈지
- 부족한 사고 요소를 유도할지
- 장면을 종료할지
- 유도가 필요할 경우 어떤 요소를 대상으로 할지

### 3.3 캐릭터 응답 모듈

캐릭터 응답 모듈은 다음 정보를 전달받습니다.

- 아이의 최신 발화
- 발화 분석 결과
- 현재 진행 모드
- 캐릭터의 감정과 상황
- 필요한 경우 유도에 사용할 캐릭터의 걱정 정보

---

## 4. 발화 분석 입력 명세

발화 분석 모듈에는 장면 정보와 아이의 최신 발화를 전달합니다.

```json
{
  "sceneContext": "현재 장면의 상황과 갈등 설명",
  "goal": "이 장면에서 아이가 생각하고 표현하도록 유도할 학습 목표",
  "previousCharacterMessage": "직전 캐릭터 발화 또는 null",
  "childUtterance": "아이의 최신 발화",
  "targetElements": [
    "PERSPECTIVE",
    "REASON",
    "SOLUTION"
  ],
  "elementCriteria": {
    "PERSPECTIVE": "이 장면에서 관점 요소로 인정할 기준",
    "REASON": "이 장면에서 이유 요소로 인정할 기준",
    "SOLUTION": "이 장면에서 해결 방법으로 인정할 기준"
  }
}
```

### 입력 필드 설명

| 필드 | 설명 |
| --- | --- |
| `sceneContext` | 현재 장면의 인물, 상황, 갈등에 대한 설명 |
| `goal` | 장면의 학습 목표 |
| `previousCharacterMessage` | 생략된 대상이나 문맥을 파악하기 위한 직전 캐릭터 발화 |
| `childUtterance` | 이번 턴에서 분석할 아이의 최신 발화 |
| `targetElements` | 해당 장면에서 주요하게 확인할 사고 요소 |
| `elementCriteria` | 해당 장면에서 각 사고 요소를 인정하기 위한 기준 |

`targetElements`는 자동으로 감지되는 정답 목록이 아닙니다.

실제 발화가 장면별 `elementCriteria`를 충족하고, 아이 발화 안에서 원문 근거가 확인될 때만 해당 요소를 인정합니다.

---

## 5. 사고 요소 분류 체계

분석 모듈은 다음 사고 요소를 사용합니다.

| 요소 | 의미 |
| --- | --- |
| `DECISION` | 선택하거나 자신의 입장을 정함 |
| `REASON` | 판단, 의견, 선택, 요청 등의 까닭을 말함 |
| `PERSPECTIVE` | 다른 인물의 상황이나 입장을 고려함 |
| `SOLUTION` | 문제를 줄이거나 해결할 구체적인 행동과 방법을 제시함 |
| `RESULT` | 행동이나 상황 이후의 결과를 설명하거나 예상함 |
| `EMOTION` | 자신이나 다른 인물의 감정을 직접 표현함 |
| `EMPATHY` | 다른 사람의 감정이나 어려움을 이해하고 배려함 |
| `REQUEST` | 특정 상대에게 행동, 말, 태도의 변화를 요구함 |

### 기본 판정 원칙

- 최신 아이 발화에서 직접 확인되는 요소만 탐지합니다.
- 아이가 말하지 않은 이유, 감정, 의도, 결과를 추론하여 추가하지 않습니다.
- 각 요소에는 아이 발화에 실제로 존재하는 원문 근거가 필요합니다.
- 같은 표현이 여러 사고 요소를 직접 충족하면 복수 탐지가 가능합니다.
- 장면 목표와 무관한 사고 요소는 목표 달성 요소로 사용하지 않습니다.
- 막연한 당위나 예의 표현만으로는 이유, 관점, 해결 방법을 인정하지 않습니다.
- 상대방에게 구체적인 행동 변화를 요구한 경우에는 `REQUEST`로 인정할 수 있습니다.

예를 들어 다음과 같은 표현은 구체적인 맥락 없이 단독으로 사용되면 사고 요소로 과대평가하지 않습니다.

```
잘해줘야 해요.
도와줘야 해요.
착하게 해야 해요.
그러면 안 돼요.
```

반면 행동 대상과 방법이 구체적으로 포함되면 장면 기준에 따라 `REQUEST` 또는 `SOLUTION`으로 인정할 수 있습니다.

## 6. 발화 분석 출력 명세

분석 결과는 다음 형식을 사용합니다.

```json
{
  "childIntent": "REASONING",
  "detectedElements": [
    {
      "type": "PERSPECTIVE",
      "evidence": "창피해서 계속 참았어요"
    }
  ],
  "utteranceValidity": "VALID"
}
```

### `childIntent`

아이 발화의 중심적인 의도를 나타냅니다.

```
QUESTION
OPINION
REASONING
SOLUTION
DECISION
PERSPECTIVE
EMOTION
REQUEST
CHALLENGE
PLAYFUL
OFF_TOPIC
SHORT_RESPONSE
UNCLEAR
```

`childIntent`는 주로 캐릭터의 반응 방식과 말투를 조정하는 데 사용합니다.

장면 목표 달성 여부는 `childIntent` 자체가 아니라 `detectedElements`를 기준으로 판단합니다.

### `detectedElements`

이번 발화에서 직접 확인된 사고 요소와 원문 근거입니다.

```json
{
  "type": "REASON",
  "evidence": "계속 참으면 더 힘들어지니까요"
}
```

### `utteranceValidity`

발화가 진행 판단에 사용할 수 있는 정보량을 나타냅니다.

```
VALID
SHORT
UNCLEAR
OFF_TOPIC
PLAYFUL
```

짧거나 불명확한 발화가 반복되면 진행 엔진에서 유도 필요성을 판단하는 신호로 사용할 수 있습니다.

---

## 7. 서버 후처리 원칙

분석 모델의 출력은 바로 사용하지 않고 서버에서 기본적인 검증을 수행합니다.

### 필수 검증 항목

1. `evidence`가 아이의 최신 발화에 실제로 포함되어 있는지 확인합니다.
2. 존재하지 않는 원문을 근거로 제시한 요소는 삭제합니다.
3. 같은 사고 요소가 한 턴에 중복 탐지된 경우 하나로 정리합니다.
4. 스키마에 정의되지 않은 요소는 제거합니다.
5. 구체성이 부족한 해결 방법 탐지는 필요에 따라 보정합니다.

후처리는 모델이 생성한 새로운 의미를 추가하는 과정이 아닙니다.

분석 결과 중 형식적으로 신뢰할 수 없는 항목을 제거하거나 정리하는 안전장치입니다.

장면 목표와 `elementCriteria`의 의미적 충족 여부는 발화 분석 모듈에서 판단합니다.

## 8. 장면별 설정 데이터

각 장면은 공통 알고리즘을 사용하되, 장면별로 다음 설정값을 다르게 가질 수 있습니다.

```json
{
  "sceneId": "scene_example",
  "goal": "장면 학습 목표",
  "requiredElements": [
    "PERSPECTIVE",
    "REASON",
    "SOLUTION"
  ],
  "elementCriteria": {
    "PERSPECTIVE": "장면별 인정 기준",
    "REASON": "장면별 인정 기준",
    "SOLUTION": "장면별 인정 기준"
  },
  "character": {
    "remainingWorries": {
      "PERSPECTIVE": "캐릭터가 아직 해소하지 못한 관점 관련 걱정",
      "REASON": "캐릭터가 아직 해소하지 못한 이유 관련 걱정",
      "SOLUTION": "캐릭터가 아직 해소하지 못한 방법 관련 걱정"
    }
  }
}
```

`goal`, `requiredElements`, `elementCriteria`는 장면의 학습·분석 기준입니다.

`remainingWorries`는 캐릭터에 속하며, 유도 시 캐릭터 모델에 전달됩니다.

같은 `REASON` 요소라도 장면에 따라 인정 기준은 달라질 수 있습니다.

예를 들어 한 장면에서는 인물의 감정을 설명하는 이유가 필요할 수 있고, 다른 장면에서는 특정 행동을 하면 안 되는 이유가 필요할 수 있습니다.

따라서 사고 요소의 이름만으로 목표 달성을 판단하지 않고, 장면별 기준을 함께 적용해야 합니다.

## 9. 진행 판단에 사용하는 상태

진행 판단 모듈은 장면 시작 이후의 상태를 누적 관리합니다.

| 상태 | 설명 |
| --- | --- |
| `turnCount` | 현재까지 아이가 발화한 횟수 |
| `newlyDetected` | 이번 턴에서 새롭게 확인된 사고 요소 |
| `accumulatedElements` | 장면 시작 이후 누적된 사고 요소 |
| `missingElements` | 필수 요소 중 아직 확인되지 않은 요소 |
| `turnsWithoutProgress` | 새로운 요소가 확인되지 않은 대화의 연속 횟수 |
| `lowInformationTurns` | 짧거나 불명확한 발화가 이어진 횟수 |
| `previousMode` | 직전 턴의 진행 모드 |
| `previousGuidanceTarget` | 직전에 유도한 사고 요소 |

누적 요소는 단순히 모델이 한 번 탐지한 모든 요소가 아니라, 장면 기준과 서버 검증을 통과한 요소를 대상으로 합니다.

---

## 10. 진행 모드

진행 판단 결과는 다음 세 가지 모드 중 하나입니다.

### 10.1 `NORMAL`

아이의 발화에 자연스럽게 반응하며 대화를 이어갑니다.

다음과 같은 상황에서 사용합니다.

- 대화가 정상적으로 진행 중인 경우
- 새로운 사고 요소가 확인된 경우
- 첫 발화인 경우
- 직전 턴에서 이미 강한 유도를 제공한 경우
- 아직 강한 개입이 필요하지 않은 경우

필요하다면 캐릭터의 남은 걱정을 약하게 드러내어 다음 사고를 자연스럽게 열 수 있습니다.

### 10.2 `GUIDED`

부족한 필수 사고 요소를 향해 대화를 조금 더 명확하게 유도합니다.

다음과 같은 신호를 종합하여 결정합니다.

- 짧거나 불명확한 발화가 반복됨
- 여러 턴 동안 새로운 사고 요소가 확인되지 않음
- 장면 종료까지 남은 대화 기회가 적음
- 필수 사고 요소가 아직 충족되지 않음

연속해서 강한 유도가 반복되지 않도록 직전 진행 모드를 함께 확인합니다.

### 10.3 `CLOSING`

장면을 종료합니다.

대표적인 종료 사유는 다음과 같습니다.

- 최소한의 대화 과정이 진행되고 필수 사고 요소가 충족됨
- 장면에서 허용한 최대 대화 범위에 도달함

`CLOSING`에서는 캐릭터 모델을 다시 호출하지 않고, 장면 설정에 정의된 종료 처리를 사용할 수 있습니다.

## 11. 진행 모드 판단 순서

정확한 내부 임계값은 장면과 서비스 운영 정책에 따라 관리하되, 판단 순서는 다음 원칙을 따릅니다.

```
1. 종료 조건 확인
   ├─ 필수 요소 충족 및 최소 대화량 충족
   └─ 최대 대화 범위 도달

2. 강한 유도 제한 조건 확인
   ├─ 첫 발화
   ├─ 이번 턴에 새로운 요소가 확인됨
   └─ 직전 턴이 GUIDED였음

3. 유도 필요성 확인
   ├─ 필수 요소가 남아 있음
   ├─ 대화가 정체됨
   ├─ 저정보 발화가 반복됨
   └─ 남은 대화 기회가 부족함

4. 위 조건에 해당하지 않으면 NORMAL
```

진행 판단의 핵심은 한 발화의 점수만 보는 것이 아니라, **누적된 사고 요소와 최근 대화 흐름을 함께 보는 것**입니다.

## 12. 유도 대상 선택

`GUIDED` 모드가 선택되면 진행 엔진은 아직 충족되지 않은 필수 요소 중 하나를 유도 대상으로 정합니다.

```json
{
  "mode": "GUIDED",
  "guidanceTarget": "SOLUTION"
}
```

유도 대상 선택 시 다음 원칙을 사용할 수 있습니다.

- 아직 충족되지 않은 필수 요소를 우선합니다.
- 직전에 유도한 요소와 동일한 요소가 반복되지 않도록 합니다.
- 장면에서 설정한 기본 우선순위를 참고할 수 있습니다.
- 아이가 방금 말한 내용과 가장 자연스럽게 연결되는 요소를 우선할 수 있습니다.

정확한 요소별 가중치와 우선순위 계산 방식은 내부 운영 설정으로 관리합니다.

## 13. 캐릭터 유도 방식

진행 엔진은 아이에게 직접 질문할 문장을 생성하지 않습니다.

진행 엔진은 부족한 사고 요소의 이름을 선택하고, 장면에 등록된 캐릭터의 `remainingWorries` 정보를 캐릭터 모델에 전달합니다.

```
부족한 요소: SOLUTION
        │
        ▼
remainingWorries.SOLUTION
        │
        ▼
캐릭터가 아직 걱정하는 내용으로 표현
```

예를 들어 부족한 요소가 `SOLUTION`인 경우에도 다음처럼 직접적인 학습 질문을 사용하지 않는 것을 원칙으로 합니다.

```
해결 방법을 말해 봐.
다른 방법은 무엇이 있을까?
```

대신 캐릭터의 상황과 감정 안에서 걱정을 드러냅니다.

```
그런데 다음에도 같은 일이 생기면 어떡하지?
```

이 구조를 통해 유도 질문이 학습지식 문항처럼 보이지 않고, 이야기 속 대화로 이어지도록 합니다.

## 14. 약한 유도와 강한 유도

### 약한 유도

`NORMAL` 모드에서 사용할 수 있습니다.

아이가 새로운 사고 요소를 말했지만 아직 필수 요소가 남아 있는 경우, 캐릭터가 다음 걱정을 가볍게 드러냅니다.

- 아이의 발화에 대한 반응이 중심
- 유도 정보는 부가적으로 사용
- 직접적인 답 요구를 최소화

### 강한 유도

`GUIDED` 모드에서 사용합니다.

대화가 반복적으로 정체되거나 남은 대화 기회가 부족한 경우, 선택된 `guidanceTarget`에 해당하는 걱정을 캐릭터의 핵심 반응으로 드러냅니다.

- 한 번에 하나의 사고 요소만 유도
- 직전 유도와 같은 형태를 반복하지 않음
- 정답이나 모범 답안을 캐릭터가 먼저 말하지 않음

## 15. 처리 결과 예시

장면의 필수 사고 요소가 다음과 같다고 가정합니다.

```
PERSPECTIVE
REASON
SOLUTION
```

### 첫 번째 발화

```
아이: 며느리가 창피해서 계속 참았던 것 같아요.
```

분석 결과 예시:

```json
{
  "childIntent": "PERSPECTIVE",
  "detectedElements": [
    {
      "type": "PERSPECTIVE",
      "evidence": "창피해서 계속 참았던 것 같아요"
    }
  ],
  "utteranceValidity": "VALID"
}
```

진행 결과 예시:

```json
{
  "mode": "NORMAL",
  "accumulatedElements": [
    "PERSPECTIVE"
  ],
  "missingElements": [
    "REASON",
    "SOLUTION"
  ]
}
```

캐릭터는 아이가 말한 며느리의 사정을 받아주고, 필요하다면 아직 남아 있는 걱정을 약하게 드러낼 수 있습니다.

### 이후 짧은 발화가 반복되는 경우

```
아이: 네.
아이: 음….
```

분석 결과에서는 새로운 사고 요소가 확인되지 않고 저정보 발화가 누적됩니다.

진행 엔진은 필수 요소가 남아 있고 대화가 정체되었다고 판단하면 다음과 같이 처리할 수 있습니다.

```json
{
  "mode": "GUIDED",
  "guidanceTarget": "REASON"
}
```

캐릭터 모델에는 `REASON`에 대응하는 캐릭터의 남은 걱정을 전달합니다.

### 필수 요소가 충족된 경우

필수 사고 요소가 모두 누적되고 장면에서 요구하는 최소한의 대화 과정이 충족되면 다음과 같이 처리합니다.

```json
{
  "mode": "CLOSING",
  "closingReason": "GOAL_MET"
}
```

최대 대화 범위에 도달한 경우에는 다음과 같이 처리할 수 있습니다.

```json
{
  "mode": "CLOSING",
  "closingReason": "MAX_TURNS"
}
```
