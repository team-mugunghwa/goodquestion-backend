# 트러블슈팅: 같은 요청이 두 번 실행되는 문제 - 동시 중복과 순차 중복

타임아웃 후 재시도된 요청이 새 요청으로 처리되어 발화가 중복 턴이 되고 별가루가
이중 차감되는 문제다. 겉보기에 "중복 실행"이라는 한 가지 문제로 보이지만, 실제로는
성격이 다른 두 문제(동시 중복과 순차 중복)가 섞여 있었다. 동시 중복은 락과 유니크
제약으로 이미 막혀 있었고, 락으로는 막을 수 없는 순차 중복을 멱등키(Idempotency-Key
헤더)로 막았다.

- 상태: 해결 (발화 제출과 아이템 구매 적용, 나머지는 위험도에 따라 후속)
- 관련 코드: `IdempotencyService`, `IdempotencyRecordStore`, `TurnController`, `ShopController`
- 회귀 테스트: `IdempotencyIntegrationTest` (7건)

---

## 1. 증상

**서버가 일을 다 마쳤는데 클라이언트만 실패로 아는 상황이 정상 범위 안에 있다.**

턴 하나의 서버 처리는 LLM 2회 순차 호출로 최악 20초인데, 모바일 HTTP 클라이언트의
기본 타임아웃이 대개 그 언저리다. 서버는 발화를 저장하고 분석하고 캐릭터 대사까지
만들었는데 응답만 네트워크에서 유실되면, 클라이언트는 실패로 판단하고 같은 요청을
다시 보낸다. 이 재전송을 서버는 구분할 방법이 없어 새 요청으로 처리한다.

상태 변경 엔드포인트 30여 개를 전수 조사한 결과, 재전송이 중복 실행되는 곳과 피해는:

| 엔드포인트 | 재전송하면 | 피해 |
| --- | --- | --- |
| 아이템 구매 | 별가루 이중 차감 + 아이템 2개 입고 | 돈. 최고 위험 |
| 발화 제출 | 같은 발화가 새 턴으로 한 번 더 처리 | 중복 턴 + LLM 요금 2배 |
| 세션 시작 | IN_PROGRESS 세션 2개 | 상태 꼬임 |
| 아이 생성 | 아이 + 행성 + 지갑 중복 | 데이터 중복 |
| story-complete | STORY 연속 구간에서 장면 스킵 | 이야기 건너뜀 |
| 단어 즐겨찾기 | 토글이라 상태가 원위치로 반전 | 상태 꼬임 |

반대로 별가루 지급(부분 유니크 인덱스), 후속 활동(session_id 유니크 + 시드 고정),
단어장(자연키 유니크), 가입(이메일 유니크), 배치(칸/아이템 유니크), 첫 대사
재생(exists 검사) 등은 유니크 제약이나 자연 멱등으로 이미 안전했다.

## 2. 원인: 중복은 한 문제가 아니라 두 문제다

같은 "중복 실행"이라도 언제 겹치느냐에 따라 원인과 해법이 완전히 다르다.

### 동시 중복 (겹침) - 두 요청이 같은 시각에 진행 중

아이가 연타해서 요청 두 개가 동시에 파이프라인을 탄다. 둘 다 같은 상태를 읽고
각자 갱신하려 하므로, **지금 진행 중인 것끼리의 조정 장치**인 락이 정확히 이
문제를 푼다. 우리는 이미 3중으로 막고 있었다.

- 낙관적 락(`story_sessions.version`): 늦게 커밋하는 쪽이 충돌 -> 409 CONCURRENT_TURN
- `messages(session_id, turn_order)` 유니크: 트랜잭션 분리로 낙관적 락이 못 잡는
  경로를 DB 제약이 메운다 -> 409 CONCURRENT_TURN
- 비관적 락(지갑 SELECT FOR UPDATE): 잔액 갱신 유실 방지

### 순차 중복 (재시도) - 첫 요청이 끝난 뒤의 같은 요청

타임아웃 후 재전송이 도착하는 시점에는 첫 요청의 트랜잭션이 **이미 커밋되고
락도 풀렸다.** 조정할 대상 자체가 없다.

- 낙관적 락: 재전송은 version을 새로 읽으므로 충돌하지 않는다
- turn_order 유니크: "마지막 + 1"로 새로 계산하므로 충돌하지 않는다
- 구매: 같은 아이템 여러 개 보유가 정상 사용이라 유니크를 걸 수조차 없다

근본 원인은 정보 부족이다. "이 요청이 아까 그 요청의 재전송인가, 새 작업인가"를
서버는 요청 내용만 봐서는 알 수 없다 - 아이가 같은 말을 진짜로 두 번 할 수도 있다.
이 구분을 아는 것은 클라이언트뿐이다.

## 3. 해법 검토

### DB 락을 더 걸면 되지 않나

안 된다. 락은 살아 있는 트랜잭션끼리의 조정이고, 순차 중복의 두 요청은 시간이
겹치지 않는다. 락을 아무리 정교하게 걸어도 이미 끝난 작업과 새 요청 사이에는
아무 일도 일어나지 않는다.

### 캐시로 응답을 기억하면 되지 않나

캐시는 해법의 대체재가 아니라 저장소 선택지다. "무엇을 키로 기억할 것인가"가
먼저인데, 그 키가 곧 멱등키다. 키가 정해진 뒤의 저장소 비교는:

| 저장소 | 문제 |
| --- | --- |
| 인메모리 캐시 | 재배포에 날아간다. push가 곧 배포인 우리 환경에서 배포 직후 재시도가 뚫린다 |
| Redis | 인프라 추가. 단일 인스턴스 MVP에 과하고, 처리 상태와 응답을 트랜잭션으로 함께 못 다룬다 |
| DB 테이블 | 유니크 제약으로 원자적 선점이 되고 본 작업과 같은 DB에 있다. 우리 규모의 정답 |

### 업계는 어떻게 하나

돈이 걸린 API의 표준 관행이 클라이언트 제공 멱등키다. Stripe가 Idempotency-Key
헤더 + 24시간 보관 + 완료 응답 재생으로 정립했고, AWS는 client token이라는 이름으로
같은 것을 쓰며, IETF에 Idempotency-Key 헤더 표준화 드래프트가 있다. 재시도는 같은
키, 새 작업은 새 키 - 클라이언트가 아는 구분을 헤더로 실어 나르는 것이 핵심이다.

정리하면:

| 문제 | 해법 | 상태 |
| --- | --- | --- |
| 동시 중복 (겹침) | 락 + 유니크 제약 | 이미 완료 |
| 순차 중복 (재시도) | 클라이언트 멱등키 + 서버 기록/재생 | 이번에 구현 |

둘은 대체재가 아니라 보완재다. 락만 있으면 재시도 중복이 남고, 멱등키만 있으면
동시 중복이 남는다.

## 4. 확정한 규약 (2026-08)

| 항목 | 내용 | 근거 |
| --- | --- | --- |
| 전달 위치 | `Idempotency-Key` HTTP 헤더 (선택) | 업계 표준 관행. 요청 본문을 안 건드려 어느 엔드포인트든 같은 방식 |
| 키 형식 | UUID 권장, 64자 이하. 초과 시 400 `INVALID_IDEMPOTENCY_KEY` | 클라이언트가 만들기 쉽고 충돌 확률 무시 가능 |
| 키 생명주기 | 작업마다 새로 생성, **재시도 사이에만 유지** | 재시도 = 같은 키, 새 작업 = 새 키. 이 구분이 규약의 전부다 |
| 완료된 키 재전송 | 저장된 응답을 그대로 재생 (작업 재실행 없음) | 클라이언트는 첫 응답과 재전송 응답을 구별할 필요가 없어야 한다 |
| 처리 중인 키 재전송 | 409 `REQUEST_IN_PROGRESS` -> 잠시 후 같은 키로 재시도 | 결과가 아직 없으므로 기다리게 한다 |
| 키 없는 요청 | 기존 동작 그대로 | 하위 호환. 프론트가 준비되는 대로 점진 적용 |
| 보관 기간 | 24시간, 1시간 주기 청소 | 재시도 창은 초-분 단위. 응답 본문을 오래 쥘 이유가 없다 |
| 적용 범위 | 발화 제출(scope: 세션), 아이템 구매(scope: 아이) | 중복 실행의 피해가 돈인 두 곳부터. 나머지는 자연 멱등화가 더 맞다 (7절) |
| 판정 주체 | 서버 (`idempotent_requests` 테이블, V6) | 클라이언트마다 판정이 갈리면 안 된다 |

## 5. 구현에서 만난 것

### PostgreSQL의 유니크 위반은 트랜잭션을 통째로 중단시킨다

처음 설계는 "insert 하고 유니크 위반 예외가 나면 기존 행을 조회"였다. PostgreSQL에서는
동작하지 않는다 - 제약 위반이 난 트랜잭션은 그 즉시 중단 상태가 되어 이후 조회가 전부
"current transaction is aborted"로 실패한다. `INSERT ... ON CONFLICT DO NOTHING`으로
위반 자체를 피하고, 삽입 행 수(1이면 선점, 0이면 기존 기록 존재)로 승패를 가리도록
바꿨다. 선점 경쟁은 여전히 유니크 제약이 심판하되 예외가 나지 않는다.

### 실패한 작업의 키는 지운다 (2026-08-18 정정: 작업이 원자적일 때만)

처음에는 작업이 실패하면(LLM 오류 등) 그 키의 기록을 무조건 삭제했다. 남겨 두면
정직한 재시도가 막혀 영영 실행되지 못한다는 이유였다. **이 판단은 절반만 옳았다.**

전제가 "실패했으면 아무것도 커밋되지 않았다"인데, 발화 처리에는 이 전제가 성립하지
않는다. 커넥션 점유를 줄이려고 턴을 트랜잭션 셋으로 쪼개 놓았기 때문이다
([트러블슈팅_턴_처리_커넥션_점유.md](트러블슈팅_턴_처리_커넥션_점유.md)).

```
① 준비(readOnly)  ② 분석 LLM  ③ 발화·분석 저장(커밋)  ④ 캐릭터 LLM  ⑤ 대사 저장
                                    ^^^^^^^^^^^^^^^^        ^^^^^^^^^^
                                    여기까지 커밋됨          여기서 실패하면
```

④에서 실패하면 아이 발화는 이미 남아 있는데 키만 사라진다. 같은 키로 재시도하면
서버는 처음 보는 요청으로 취급해 ①부터 다시 돌리고, **같은 발화가 두 번 저장되고
턴 수가 두 번 오르고 분석 LLM이 두 번 과금된다.** 멱등키가 막겠다고 선언한 바로 그
피해를, 멱등키의 실패 처리가 만들어 낸다.

주목할 점은 **두 결정이 각각은 옳았다**는 것이다. 턴을 쪼갠 것도, 실패한 키를 지운
것도 그 자체로는 근거가 있었다. 둘이 만나는 지점을 아무도 보지 않았을 뿐이다.

그래서 엔드포인트마다 "실패한 요청을 같은 키로 다시 실행해도 되는가"를 선언하게
바꿨다(`IdempotentEndpoint.isReexecutable`).

| 엔드포인트 | 재실행 | 실패 시 | 이유 |
| --- | --- | --- | --- |
| 아이템 구매 | 가능 | 키 삭제 | 검증, 차감, 입고가 한 트랜잭션이라 전부 롤백된다 |
| 발화 제출 | 불가 | FAILED로 기록 | 앞 구간이 이미 커밋됐을 수 있다 |

발화가 실패로 닫힌 키에 같은 키가 다시 오면 재실행 대신 409
`REQUEST_ALREADY_FAILED`를 내린다. 클라이언트는 `turn-state`로 실제 상태를 확인하고,
새 턴이 필요하면 **새 키로** 보낸다. 실패한 것은 그 시도이지 아이의 발화가 아니다.

서버는 어느 구간에서 실패했는지 모르므로 보수적으로 전부 남긴다. 여기처럼 ② 분석
단계에서 실패해 실제로는 아무것도 커밋되지 않은 경우도 재실행하지 않는다. 정확히
가르려면 작업 쪽이 "어디까지 커밋했는지"를 알려 줘야 하는데, 그 결합을 만드는 대신
안전한 쪽으로 기울였다. 대가는 새 키 발급 한 번이다.

**테스트가 이 문제를 놓친 이유도 기록해 둔다.** 기존 실패 테스트는 분석 대역이
예외를 던지게 만들었는데, 그건 ② 단계라 아직 아무것도 커밋되지 않은 안전한 경로였다.
위험한 경로(③ 커밋 후 ④ 실패)는 테스트가 없었다. **테스트가 있다는 사실이 오히려
안심시킨 경우**다. 지금은 재실행되지 않음과 새 키가 동작함을 각각 고정했다.

### 오래된 처리 중 기록을 뺏지 않는다

완료 기록 직전에 서버가 죽으면 그 키는 IN_PROGRESS로 남아 청소 전까지 409를 받는다.
"오래된 기록은 뺏어서 다시 실행"하는 설계도 가능하지만 하지 않았다 - 작업이 이미
커밋된 뒤 기록만 못 남긴 경우를 뺏어 재실행하면, 막으려던 중복 실행이 그대로
재발한다. 이 극단 케이스의 복구는 기존 절차(turn-state 확인)를 쓴다.

### 재생에도 소유권 검증이 필요하다

재생 경로는 본 작업을 건너뛰므로 본 작업 안의 소유권 검증도 건너뛴다. 기록에
보호자 id를 함께 남기고 재생 전에 대조한다 - 다르면 없는 기록으로 취급한다.

## 6. 전후 비교

| 상황 | 전 | 후 (키 사용 시) |
| --- | --- | --- |
| **발화 타임아웃 후 재전송** | **같은 발화가 새 턴으로 중복 처리 (LLM 요금 2배)** | **저장된 응답 재생, 중복 없음** |
| **구매 타임아웃 후 재전송** | **별가루 이중 차감** | **저장된 응답 재생, 단일 차감** |
| 재전송 전 클라이언트 절차 | turn-state 조회 후 3분기 판정 표 | 같은 키로 그대로 재전송 |
| 처리 중 재전송 | 409 CONCURRENT_TURN (동시일 때만) | 409 REQUEST_IN_PROGRESS (순차도 잡음) |
| 재시도와 새 발화의 구분 | 서버가 추측 불가 | 키로 자동 구분 |
| 아이 연타 (동시 중복) | 409 CONCURRENT_TURN | 동일 (락이 계속 담당) |

확인 기준은 `IdempotencyIntegrationTest`다. 특히 "같은 키의 재전송이 저장된 응답을
재생하고 턴을 중복 처리하지 않는다" 테스트는 분석 대역이 대본 없이는 예외를 던지는
성질을 이용한다 - 재전송에서 예외가 안 났다는 것 자체가 작업이 재실행되지 않았다는
증거다.

## 7. 남은 것

전수 조사에서 나온 나머지 무방비 엔드포인트는 멱등키보다 **자연 멱등화**(요청 자체를
몇 번 보내도 같아지게 만드는 것)가 더 맞는 곳들이라 별도 작업으로 미뤘다.

- 세션 시작: 같은 아이의 IN_PROGRESS 세션이 있으면 새로 만들지 않고 그것을 반환
- 단어 즐겨찾기: 토글(반전) 대신 목표 상태를 요청에 실어 절대값 설정으로
- ~~story-complete~~: **완료(2026-08-18).** 다 본 장면 id를 요청에 실어 현재 장면과
  다르면 전진하지 않고 현재 상태를 돌려준다. 클라이언트가 헤더를 챙기지 않아도
  동작하는 것이 멱등키 대비 이점이다 - 상태로 알 수 있는 것은 상태로 푼다.
  지금은 선택 파라미터라 구버전 클라이언트는 전과 같이 동작하고, 클라이언트가
  모두 올라오면 필수로 바꾼다. 회귀 테스트 `SceneAdvanceIdempotencyTest`.
- 아이 생성: 빈도가 낮고 삭제로 복구 가능해 우선순위 낮음

## 8. 곁가지로 고친 것

**세션 중단에 상태 가드가 없었다.** `stop()`이 상태를 보지 않고 STOPPED로 바꿔,
이미 완주한 세션에 중단 요청이 도착하면 COMPLETED를 덮었다. `completedAt`은 남아
있어 "끝냈는데 중단됨"이라는 모순 상태가 되고, 홈의 이어하기와 리포트가 서로 다른
이야기를 하게 된다. 화면을 닫으며 보낸 중단 요청이 완주 직후에 도착하는 것은 드문
일이 아니다.

진행 중일 때만 멈추게 하고, 중단할 것이 없으면 조용히 넘어간다 - 이미 끝난 세션을
닫으려는 것은 오류가 아니라 늦은 요청이다. 이것도 자연 멱등의 한 형태다.

그 외, 발화 밖의 모든 유니크 충돌(가입 동시 요청, 단어장 동시 추가, 배치 race 등)이
전역 핸들러 부재로 500으로 나가는 문제가 있다. `DataIntegrityViolationException`을
도메인별 409로 바꾸는 정리가 필요하다.
