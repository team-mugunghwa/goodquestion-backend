# 트러블슈팅: 대화 턴 처리 중 DB 커넥션 고갈

발화 한 건을 처리하는 동안 DB 커넥션이 묶여, 대화와 무관한 API까지 함께 막히는 문제다.
LLM 어댑터를 붙이기 전에 발견해 재현부터 해결까지 마쳤다. 커넥션 점유 시간이 4076밀리초에서
55밀리초로 줄었고, 대화가 몰려도 로그인이 정상 응답한다.

- 상태: 해결 (재시도 중복 방지는 클라이언트 규약 합의 후 착수)
- 관련 코드: `TurnOrchestrator`, `TurnTransactions`, `WebClientConfig`, `TurnTimer`
- 회귀 테스트: `TurnConnectionExhaustionTest`, `TurnConcurrencyTest`

---

## 1. 증상

아이 몇 명이 동시에 말하면 **대화와 아무 상관 없는 요청까지 실패한다.** 로그인이 대표적이다.

"대화가 느리다"가 아니라 "대화 때문에 서비스 전체가 멈춘다"가 문제의 성격이다. 대화 기능이
느린 것은 LLM을 쓰는 이상 어느 정도 감수할 일이지만, 그 대가를 로그인이 치를 이유는 없다.

발견 시점에는 LLM 어댑터가 아직 501 스텁이라 실제로 겪지는 않았다. 스텁은 즉시 예외로
빠지고 테스트 대역은 즉시 응답하므로 문제가 드러나지 않는다. gpt-5-mini를 붙이는 순간
나타나는 종류의 문제다.

## 2. 재현

`TurnConnectionExhaustionTest`가 이 상황을 만든다.

| 조건 | 값 | 이유 |
| --- | --- | --- |
| 커넥션 풀 크기 | 2 | 운영 기본값 10에서도 같은 일이 벌어진다. 고갈에 필요한 수가 유한하다는 것이 문제지 그 수가 10이라는 것이 문제가 아니다 |
| LLM 응답 지연 | 2초 x 2회 | 추론 모델의 응답 시간을 가정 |
| 동시 발화 | 2건 | 풀을 정확히 채우는 수 |

두 발화가 LLM 응답을 기다리는 상태에 들어간 것을 확인한 뒤 로그인을 호출한다. 타이밍은
`sleep`으로 어림잡지 않고, LLM 대역이 호출되는 순간 래치를 내려 맞춘다. 그 시점이면 발화
저장이 끝나 커넥션을 이미 쥐고 있다.

### 결과

```
턴 처리 sessionId=44eb7cdd... 총 4076ms (저장 8ms, 분석 2048ms, 판단 0ms, 대사 2017ms)

로그인 소요 1013ms, 결과 CannotCreateTransactionException

HikariPool-1 - Connection is not available, request timed out after 1006ms
  (total=2, active=2, idle=0, waiting=0)
```

읽을 점 세 가지다.

- `active=2, idle=0` - 커넥션 두 개를 대화가 다 쥐고 있다
- 로그인은 `CannotCreateTransactionException`으로 끝났다. **쿼리를 던져보지도 못하고
  트랜잭션 시작 자체에서 실패했다.** 로그인이 무거워서가 아니라 순서를 못 받은 것이다
- 턴 4076밀리초 중 DB가 실제로 일한 시간은 30밀리초 남짓이다. 나머지는 LLM 대기다

## 3. 원인

### 트랜잭션이 곧 커넥션이다

`@Transactional` 메서드는 첫 DB 접근에서 풀의 커넥션 하나를 빌리고, 커밋하거나 롤백할
때까지 돌려주지 않는다. 그 사이 무엇을 하든 상관없다. DB를 쓰지 않고 외부 API 응답을
기다리기만 해도 커넥션은 계속 묶여 있다.

`TurnOrchestrator.processUtterance`가 `@Transactional`이고, 안에서 부르는
`analysisService.analyze`와 `messageService.append`는 전파 설정이 기본값(REQUIRED)이라
새 트랜잭션을 열지 않고 바깥 트랜잭션에 합류한다. **턴 하나가 트랜잭션 하나다.**

### 시간축

```
[커넥션 대여]
  |
  +- INSERT 아이 메시지            8ms    DB 사용
  +- 분석 LLM 호출              2048ms    DB 놀고 있음   <- 커넥션 쥔 채로
  +- INSERT 분석 결과, 누적 갱신     0ms    DB 사용
  +- 진행 판단                     0ms    순수 계산
  +- 캐릭터 LLM 호출            2000ms    DB 놀고 있음   <- 커넥션 쥔 채로
  +- INSERT 캐릭터 메시지, 세션 갱신 17ms    DB 사용
  |
[커밋, 커넥션 반납]              총 4076ms
```

점유 시간의 99% 이상을 아무 일도 하지 않으면서 붙들고 있다.

### 왜 다른 API까지 막히는가

커넥션 풀은 **앱 전체가 공유하는 자원**이다. 로그인도, 홈 조회도, 상점도 같은 풀을 쓴다.
대화가 풀을 다 가져가면 나머지는 대기열에 서고, Hikari 기본 대기 시간 30초를 넘기면
예외가 난다.

운영 기본값으로 계산하면 이렇다. 풀 10개, 턴 하나가 5초를 점유한다고 하면 동시에 처리
가능한 대화는 10건, 처리량은 초당 2턴이다. 열한 번째 아이가 말하는 순간부터 서비스 전체가
멈춘다.

### 상한이 없다는 점

여기에 `WebClientConfig`가 비어 있어 외부 호출에 타임아웃이 없었다. 벤더가 응답하지 않으면
위 그림의 2048밀리초 자리가 무한대가 된다. 커넥션은 영영 반납되지 않고, Postgres의
`idle_in_transaction_session_timeout`도 기본 미설정이라 서버가 끊어주지도 않는다.

한 번 막히면 재기동 말고는 풀리지 않는 상태였다.

## 4. 왜 이렇게 짜였나

의도적인 선택이었고, 그 선택에 나름의 근거가 있었다는 점을 적어 둔다.

턴 하나를 한 트랜잭션으로 묶으면 **중간에 무엇이 실패하든 없던 일이 된다.** 캐릭터 LLM이
실패했는데 아이 발화만 저장돼 있는 상태, 분석은 저장됐는데 세션 누적은 갱신되지 않은 상태
같은 것이 생기지 않는다. 대화 기록과 진행 상태가 어긋나면 복구가 까다로운 도메인이라
원자성을 우선한 것은 자연스럽다.

문제는 그 트랜잭션 안에 외부 호출이 들어 있다는 것이지 트랜잭션 자체가 아니다. 외부 호출은
DB 트랜잭션이 보장해 주는 것이 아무것도 없으면서 시간만 길다.

## 5. 적용한 것

### 5-1. 외부 호출 타임아웃 (완료)

`WebClientConfig`에 연결 3초, 응답 10초를 걸었다. `HTTP_CONNECT_TIMEOUT_MS`,
`HTTP_RESPONSE_TIMEOUT_MS`로 재배포 없이 조정할 수 있다.

재시도는 **연결 실패에만** 1회 건다. 응답 타임아웃은 재시도하지 않는다.

- 서버가 이미 요청을 받아 처리 중일 수 있어 같은 발화가 두 번 처리될 수 있다
- LLM은 호출당 과금이다
- 10초를 기다렸다 또 10초를 기다리면 아이는 마이크 앞에서 20초를 보낸다

연결 실패는 다르다. 서버에 닿지도 못했으므로 아무것도 보내지지 않았고, 다시 보내도 중복이
생기지 않는다.

주의할 점이 하나 있다. `responseTimeout`은 응답 전체의 마감이 아니라 **읽기와 읽기 사이의
최대 간격**이다. 한 번에 내려오는 JSON에서는 사실상 마감처럼 동작하지만, 스트리밍으로
바꾸면 조각이 계속 도착하는 한 시간 제한이 걸리지 않는다. 그때는 호출부에서 전체 시간을
따로 걸어야 한다.

본문 로깅은 넣지 않았다. 이 클라이언트가 실어 나르는 것은 아이 발화 원문과 벤더 API 키다.

### 5-2. 구간별 소요 시간 계측 (완료)

`TurnTimer`가 저장, 분석, 판단, 대사 네 구간을 재고 턴마다 한 줄을 남긴다.

```
턴 처리 sessionId=... 총 4076ms (저장 8ms, 분석 2048ms, 판단 0ms, 대사 2017ms)
```

실패해도 남긴다. 외부 호출이 타임아웃으로 끊겼을 때가 이 숫자를 가장 보고 싶은 순간이다.
발화 원문이나 캐릭터 대사는 담지 않는다. 시간을 보려고 남기는 로그에 대화 내용이 딸려
들어가면 그때부터 로그 보관 기간이 개인정보 문제가 된다.

### 5-3. 트랜잭션 경계 분리 (완료)

외부 호출을 트랜잭션 밖으로 뺀다. 커넥션 점유가 4076밀리초에서 30밀리초 수준으로 떨어진다.
`backend-dev-guide.md`의 파이프라인 설계에 분석 단계가 "트랜잭션 밖"이라고 적힌 것도 이
구조를 전제한 것이다.

나누는 지점은 두 가지를 놓고 골랐다.

```
안 1) 저장을 먼저 한다 - 기존 코드 순서 그대로

[쓰기 1] 소유권·상태 확인, 아이 메시지 저장      -> 커밋
         분석 LLM 호출                            (트랜잭션 밖)
[쓰기 2] 분석 저장, 누적 갱신, 진행 판단 기록    -> 커밋
         캐릭터 LLM 호출                          (트랜잭션 밖)
[쓰기 3] 캐릭터 메시지 저장, 장면 이동           -> 커밋

안 2) 분석을 먼저 한다 - 채택

[읽기 1] 소유권·상태 확인, 분석 입력 준비        -> 커밋
         분석 LLM 호출                            (트랜잭션 밖, 아직 저장된 것 없음)
[쓰기 1] 아이 메시지, 분석, 누적, 판단 기록      -> 커밋
         캐릭터 LLM 호출                          (트랜잭션 밖)
[쓰기 2] 캐릭터 메시지 저장, 장면 이동           -> 커밋
```

안 2를 고른 이유는 **부분 상태의 가짓수가 줄기 때문**이다. 분석 LLM은 발화 텍스트만 있으면
되고, `Message` 객체가 필요한 것은 분석 결과에 외래키를 걸기 위해서다. 순서를 바꾸면 첫
외부 호출 전까지 커밋된 것이 없으므로 "아이 메시지만 남고 분석은 없는" 상태가 아예 생기지
않는다.

**트랜잭션 개수는 양쪽 다 셋으로 같다.** 안 2는 쓰기가 둘로 줄지만, 대신 LLM을 부르기 전에
소유권과 장면 상태를 확인할 읽기 트랜잭션이 하나 필요해진다. 그 확인을 생략할 수는 없다 -
남의 세션이거나 이미 끝난 장면인데 LLM부터 부르면 돈과 시간을 쓰고 나서 거절하게 된다.
줄어드는 것은 트랜잭션 수가 아니라 중간에 남을 수 있는 상태의 가짓수다.

실제 작업량은 애노테이션을 떼는 데 있지 않았다. 트랜잭션이 끝나면 `StorySession`이 detached가
되고 `open-in-view: false`라서 LAZY 연관에 접근하는 순간 예외가 난다. 기존 코드는 한 트랜잭션
안이라는 전제로 세션 객체를 계속 들고 다녔으므로, **구간 사이를 엔티티가 아니라 값으로 건너도록**
바꾸는 것이 작업의 대부분이었다.

경계를 넘는 값은 record로 만들어 이름을 붙였다.

| record | 무엇을 건너나 |
| --- | --- |
| `SceneAnalysisContext` | 분석 LLM에 넘길 장면 값 |
| `AnalysisOutcome` | 분석과 후처리는 끝났고 아직 저장되지 않은 결과 |
| `CharacterPrompt` | 캐릭터 LLM 입력. 고정 마무리 대사도 여기 담긴다 |
| `ChildTurnRecord` | 아이 턴 트랜잭션이 남긴 것. 응답 조립에 쓴다 |
| `TurnClosure` | 캐릭터 대사 트랜잭션이 남긴 것 |

트랜잭션 구간은 `TurnTransactions`로 뺐다. `TurnOrchestrator`의 private 메서드로 두면
자기 호출이 프록시를 타지 않아 `@Transactional`이 걸리지 않는다.

구간마다 세션을 다시 읽고 상태를 다시 확인한다. 사이에 수 초가 흐르므로 앞 구간에서 본 상태가
그대로라고 가정할 수 없다. 다만 마지막 구간은 예외로, 최대 턴에 닿아 닫히는 턴이 정상 경로라
진입 검사를 그대로 적용하면 자기 자신을 거절하게 된다.

몇 가지가 함께 정리됐다.

- 아이 이름 치환을 저장 직전 한 곳으로 모았다. 규칙은 세션이 들고 있으므로 트랜잭션 밖에서
  복제할 수 없고, 복제하면 첫 대사와 마지막 대사가 갈린다
- 고정 마무리 대사 판단이 `CharacterResponseService` 한 곳으로 모였다. 고정 대사가 있으면
  LLM을 아예 부르지 않으므로 **그 턴은 외부 호출이 한 번뿐이다**
- `SceneClosingHandler`에서 LLM 호출이 빠졌다. 저장과 장면 이동만 한다

### 5-4. 겹친 발화의 409 변환 (완료)

트랜잭션을 쪼개면서 동시 발화가 실패하는 방식이 달라졌다. 전에는 턴 전체가 한 트랜잭션이라
낙관적 락이 먼저 잡아 409로 나갔는데, 지금은 발화 저장이 먼저 커밋되므로 messages의
`unique (session_id, turn_order)`가 먼저 걸린다. 그대로 두면 500이다.

```
ConstraintViolationException: duplicate key value violates unique constraint
  "messages_session_id_turn_order_key"
```

`turn_order`를 마지막 값 더하기 1로 계산하기 때문에, 앞선 턴이 커밋되기 전에 다음 턴이 값을
읽으면 둘이 같은 번호를 잡는다.

변환은 전역 예외 핸들러가 아니라 `TurnOrchestrator`에서 한다. 무결성 충돌을 전역에서
409 `CONCURRENT_TURN`으로 바꾸면 가입 이메일 중복이나 배치 칸 중복까지 "앞선 발화를 처리하는
중입니다"라고 답하게 된다. 그 의미는 턴 처리 안에서만 성립한다.

원래 예외는 warn으로 남긴다. 무결성 충돌이 동시 발화가 아닌 다른 이유로 났다면 그것은 결함인데,
409로 덮어쓰기만 하면 드러날 자리가 없어진다.

`TurnConcurrencyTest`가 세 건을 동시에 던져 실패의 모양을 확인한다. 검사하는 것은 "충돌이
반드시 난다"가 아니라 "겹친 요청이 어떻게 끝나든 409로 나간다"는 점이다. 실제로는 세 건 중
두 건이 매번 충돌한다.

### 5-5. 커넥션 풀 설정 명시 (완료)

설정이 없어 Hikari 기본값이 조용히 적용되고 있었다. 조용히 적용되는 값은 튜닝 대상으로 보이지
않는다. 세 가지를 명시했다.

| 항목 | 값 | 근거 |
| --- | --- | --- |
| `maximum-pool-size` | 10 (`DB_POOL_SIZE`) | 기본값과 같다. 인스턴스를 여러 개 띄우면 이 값 곱하기 인스턴스 수가 DB 연결 상한을 넘지 않아야 한다 |
| `connection-timeout` | 3초 | 기본값 30초는 장애를 30초 동안 느린 응답으로 감춘다. 55ms짜리 트랜잭션이라면 3초를 못 기다리는 것은 대기가 아니라 장애다 |
| `leak-detection-threshold` | 2초 | 이 시간을 넘겨 커넥션을 쥐면 경고와 스택트레이스를 남긴다 |

마지막 항목이 이 문서와 직접 이어진다. **외부 호출이 트랜잭션 안으로 다시 들어오는 회귀를
잡는 그물이다.**

값을 2초로 잡은 이유가 있다. Hikari가 허용하는 최솟값이 2초다. 정상 점유는 턴 처리 55밀리초,
기동 시 Flyway 90밀리초라 스무 배 넘는 여유가 있다. 반대로 처음 잡았던 5초로 두면 이 문서가
다루는 4076밀리초짜리 점유를 그대로 통과시킨다 - **여유를 크게 잡을수록 안전한 설정이 아니다.**

전체 테스트에서 오탐이 없고, 2.5초를 쥐는 트랜잭션에서는 경고가 뜨는 것을 확인했다.

#### 왜 풀을 키우지 않았나

커넥션이 부족해서 생긴 문제였으니 풀을 키우면 되지 않느냐는 물음이 자연스럽게 나온다.
그러지 않은 이유를 적어 둔다.

**풀은 처리량 손잡이가 아니다.** 풀을 키운다고 DB가 더 빨리 일하지 않는다. Postgres는 커넥션
하나당 프로세스 하나를 띄우므로, 커넥션이 늘면 늘어나는 것은 처리량이 아니라 동시에 경쟁하는
프로세스 수다. 컨텍스트 스위칭과 락 경합, 공유 버퍼 경합이 함께 늘어 어느 지점을 넘으면
처리량이 오히려 떨어진다. 그래서 풀 크기는 "요청이 몇 개 들어오나"가 아니라 "DB가 실제로
병렬 처리할 수 있는 양이 얼마나 되나"에 맞춘다. 보통 코어 수의 두 배 언저리다.

**우리 숫자로는 이미 과하다.** 턴 하나가 커넥션을 쓰는 시간은 세 구간을 합쳐 79밀리초다
(준비 11 + 판단 55 + 반영 13). 커넥션 10개면 초당 약 126턴이다.

아이 수로 바꾸면 규모가 보인다. 아이 한 명이 말하고 LLM이 답을 만들고 그 답을 듣는 데 20초쯤
걸린다고 하면, 아이 한 명은 20초마다 79밀리초만 커넥션을 쓴다. 커넥션 하나의 0.4%다.
**10개로 동시 접속 수천 명을 감당한다.** MVP에서 닿을 숫자가 아니다.

트랜잭션 분리 전이었다면 답이 달랐다. 그때는 턴 하나가 4076밀리초를 점유해 풀 10개로 동시
대화 10건이 한계였고, 풀을 키우는 것이 임시방편이라도 됐다. 지금은 그 병목 자체가 없다.

**키우면 두 가지가 나빠진다.**

- 인스턴스 수만큼 곱해진다. 앱을 세 개 띄우면 실제 연결 수는 풀 크기의 세 배이고 여기에
  마이그레이션과 관리 도구가 붙는다. `max_connections`를 넘으면 그때부터 모든 클라이언트가
  연결을 얻지 못한다. 앱 기동 자체가 실패한다
- 문제를 감춘다. 지금 상태에서 커넥션 10개가 마른다면 그것은 부하가 아니라 결함이다. 긴
  트랜잭션이 다시 생겼다는 뜻이다. 풀이 크면 그것이 "조금 느리네" 정도로 흡수돼 원인을 찾지
  못한 채 몇 주가 지난다. 작은 풀과 3초 타임아웃, 2초 누수 경고는 그 순간 시끄럽게 알리려고
  맞춘 조합이다

**올려야 하는 시점은 측정으로 정한다.** 두 가지가 동시에 보일 때다.

1. 커넥션 대기 큐가 계속 쌓인다 (`hikaricp.connections.pending`)
2. 그런데 DB CPU는 놀고 있다

앞은 맞는데 뒤가 아니라면(DB가 이미 포화) 풀을 키울수록 나빠진다. 지금은 그 판단을 할 근거가
없다. actuator가 health만 노출하고 있어 Hikari 지표가 나오지 않는다. 부하가 실제로 걱정되는
시점이 오면 `metrics` 노출을 열고 대기 큐부터 보는 것이 순서다.

`DB_POOL_SIZE`를 환경변수로 뺀 이유가 여기 있다. 필요해지면 재배포 없이 올리되, 근거가 생기기
전까지는 기본값으로 둔다.

## 6. 전후 비교

같은 조건(풀 2, LLM 2초씩, 동시 발화 2건)에서 잰 값이다.

| 항목 | 전 | 후 |
| --- | --- | --- |
| **동시 대화 중 로그인** | **1013ms 후 실패** | **102ms 성공** |
| **커넥션 최대 점유 시간** | **4076ms** | **55ms** |
| 벤더 무응답 시 대기 | 무한 | 최대 10초 |
| 연결 실패 시 | 즉시 실패 | 1회 재시도 |
| 막힌 뒤 복구 | 재기동 | 자동 |
| 어디서 시간이 가는지 | 알 수 없음 | 턴마다 구간별 로그 |
| 겹친 발화 응답 | 409 (낙관적 락) | 409 (무결성 충돌 변환) |
| 턴 하나 소요 | 4076ms | 4098ms (변화 없음) |
| 중간 실패 시 상태 | 전부 롤백 | 부분 커밋 (7절 참고) |

로그인이 실패에서 성공으로 바뀐 것이 이번 작업의 목적이다.

턴 자체는 빨라지지 않았고 그것이 맞다. 느린 원인은 LLM이지 트랜잭션이 아니었다. 바뀐 것은
**그 느림이 다른 요청에 옮지 않는다**는 점이다.

구간별 로그를 보면 무엇이 달라졌는지 그대로 보인다.

```
전: 총 4076ms (저장 8ms, 분석 2048ms, 판단 0ms, 대사 2017ms)
      -> 커넥션 하나가 4076ms 내내 묶임

후: 총 4098ms (준비 11ms, 분석 2012ms, 판단 55ms, 대사 2004ms, 반영 13ms)
      -> 커넥션은 준비 11ms, 판단 55ms, 반영 13ms 세 번만 짧게 빌린다.
         분석과 대사 구간에는 커넥션을 들고 있지 않다.
```

가장 긴 단일 트랜잭션이 55밀리초이고, 턴 하나가 커넥션을 쓰는 시간은 세 번을 합쳐 79밀리초다.
풀 10개면 이론상 초당 126턴이다. 실제 상한은 커넥션이 아니라 LLM 벤더의 처리량이 정한다.
원래 그래야 하는 모양이다.

확인 기준은 `TurnConnectionExhaustionTest`다. 분리 전까지 실패하던 로그인 검증이 통과로
바뀌었고, 다시 한 트랜잭션으로 묶는 변경이 들어오면 여기서 걸린다.

## 7. 남은 것

### 트랜잭션 분리의 대가와 중복 방지

원자성을 잃었다. 캐릭터 LLM이 실패하면 아이 발화와 분석은 커밋된 채 캐릭터 대사만 없는
상태가 남는다. 클라이언트가 그대로 재시도하면 같은 발화가 또 쌓이고 턴 카운트가 두 번 오른다.

복구 경로 자체는 이미 있다. `GET /api/sessions/{sessionId}/turn-state`와 이어하기가 구현돼
있어 클라이언트가 현재 상태를 다시 읽을 수 있다. 정해야 하는 것은 중복 방지 방식이다.

#### 실패 상황부터 나누기

말로 비교하면 답이 나오지 않아서, 무엇이 실패하는지부터 나눴다.

| | 상황 | 멱등키 | 메시지 처리 상태 |
| --- | --- | --- | --- |
| S1 | 분석 LLM 타임아웃 (아이 메시지만 커밋됨) | 막음 | 막음 |
| S2 | 캐릭터 LLM 타임아웃 (발화, 분석, 누적까지 커밋됨) | 막음 | 막음 |
| S3 | 서버는 다 성공했는데 응답이 안 닿음 | 막음 | **못 막음** |
| S4 | 아이가 마이크를 두 번 눌러 서로 다른 요청이 겹침 | 못 막음 | 못 막음 |

안 2를 채택했으므로 S1은 생기지 않는다. S4는 두 방식 모두 해결하지 못하는 별개 문제다.
따라서 선택은 S3 하나로 갈린다.

#### S3이 갈림길인 이유

메시지 처리 상태 방식은 "미완 메시지가 있으면 이어서 처리한다"로 동작한다. 그런데 S3에서는
턴이 이미 완결됐으므로 미완 메시지가 없다. 재시도가 그대로 새 턴으로 쌓인다.

그리고 S3은 예외적인 상황이 아니라 **가장 흔한 재시도 사유**다. 턴 하나의 최악 소요가
20초(LLM 10초씩 두 번)인데 모바일 HTTP 클라이언트의 기본 타임아웃은 대개 그 언저리다.
서버는 일을 다 마쳤는데 클라이언트가 먼저 포기하는 상황이 정상 범위 안에 있다.

#### 이 도메인에서만 생기는 문제

메시지 처리 상태 방식은 "재시도"와 "아이가 다시 말한 것"을 구분하지 못한다.

응답이 오지 않으면 아이는 다시 말한다. 그것이 이 서비스의 정상 흐름이고 `stt_retry_count`
컬럼이 그 증거다. 그런데 다시 말하면 STT 결과가 달라진다. 미완 메시지를 이어받는 방식은
아이가 방금 한 말이 아니라 이전 말을 분석하게 된다.

멱등키는 이 구분이 자동으로 된다. 재시도는 같은 키, 다시 말한 것은 새 키다. 클라이언트가
어느 쪽인지 알고 있으므로 서버가 추측할 필요가 없다.

#### 결론: 멱등키

메시지 처리 상태 방식이 하려던 일은 멱등 레코드의 상태 컬럼이 이미 한다. 반대는 성립하지
않는다. 포함 관계라 고민할 여지가 크지 않았다.

```
utterance_requests
  session_id, idempotency_key   -- unique
  status                        -- IN_PROGRESS / COMPLETED
  response                      -- jsonb, 완료 시 저장
```

`messages`에 컬럼을 얹지 않고 별도 테이블로 둔다. 응답 본문은 대화 기록과 성격이 다르고
보관 기간도 다르게 가져갈 수 있다. 멱등 레코드는 며칠이면 충분하다.

대가는 클라이언트 규약 하나다. 키를 발화마다 만들고 **재시도 사이에 유지**해야 한다.
재시도할 때 키를 새로 만들면 아무 효과가 없다.

### 동시 발화(S4)의 남은 부분

응답은 409로 정리했다(5-4). 남은 것은 실패한 쪽이 남기는 흔적이다.

전에는 턴 전체가 한 트랜잭션이라 충돌하면 통째로 롤백됐다. 지금은 발화 저장이 먼저 커밋되므로,
겹친 요청 중 진 쪽이 아이 메시지만 남기고 끝날 수 있다. 클라이언트에게는 409로 안내되지만
대화 기록에는 대답 없는 발화가 하나 남는다.

멱등키를 넣으면서 함께 정리하는 것이 자연스럽다. 미완 상태를 어떻게 다룰지가 같은 문제이기
때문이다.

### DB 연결 상한 확인

풀 크기는 명시했지만(5-5), 인스턴스를 여러 개 띄웠을 때 풀 크기 곱하기 인스턴스 수가 Railway
Postgres의 연결 상한을 넘지 않는지는 확인하지 못했다. 코드가 아니라 Railway 대시보드에서
봐야 하는 값이다.

풀을 키울 일이 생기면 이 확인이 먼저다. 근거와 판단 기준은 5-5의 "왜 풀을 키우지 않았나"에
적어 두었다.

### 타임아웃 계층 정합성

LLM 10초를 두 번 부르니 최악 20초에 처리 시간이 붙는다. 바깥쪽 타임아웃(Railway 프록시,
프론트 HTTP 클라이언트)이 이보다 길어야 안쪽이 먼저 끊긴다. 바깥이 먼저 끊기면 서버는 계속
일하는데 클라이언트만 포기하는 상태가 된다.
