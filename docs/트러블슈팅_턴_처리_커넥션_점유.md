# 트러블슈팅: 대화 턴 처리 중 DB 커넥션 고갈

발화 한 건을 처리하는 동안 DB 커넥션이 묶여, 대화와 무관한 API까지 함께 막히는 문제다.
LLM 어댑터를 붙이기 전에 발견해 재현과 상한 설정까지 마쳤고, 근본 원인인 트랜잭션 경계
분리는 아직 남아 있다.

- 상태: 진행 중 (타임아웃과 계측 적용 완료, 트랜잭션 분리 예정)
- 관련 코드: `TurnOrchestrator`, `WebClientConfig`, `TurnTimer`
- 재현 테스트: `TurnConnectionExhaustionTest`

---

## 1. 증상

아이 몇 명이 동시에 말하면 **대화와 아무 상관 없는 요청까지 실패한다.** 로그인이 대표적이다.

"대화가 느리다"가 아니라 "대화 때문에 서비스 전체가 멈춘다"가 문제의 성격이다. 대화 기능이
느린 것은 LLM을 쓰는 이상 어느 정도 감수할 일이지만, 그 대가를 로그인이 치를 이유는 없다.

발견 시점에는 LLM 어댑터가 아직 501 스텁이라 실제로 겪지는 않았다. 스텁은 즉시 예외로
빠지고 테스트 대역은 즉시 응답하므로 문제가 드러나지 않는다. gpt-5-mini를 붙이는 순간
나타나는 종류의 문제다.

## 2. 재현

`TurnConnectionExhaustionTest`가 이 상황을 만든다.

| 조건 | 값 | 이유 |
| --- | --- | --- |
| 커넥션 풀 크기 | 2 | 운영 기본값 10에서도 같은 일이 벌어진다. 고갈에 필요한 수가 유한하다는 것이 문제지 그 수가 10이라는 것이 문제가 아니다 |
| LLM 응답 지연 | 2초 x 2회 | 추론 모델의 응답 시간을 가정 |
| 동시 발화 | 2건 | 풀을 정확히 채우는 수 |

두 발화가 LLM 응답을 기다리는 상태에 들어간 것을 확인한 뒤 로그인을 호출한다. 타이밍은
`sleep`으로 어림잡지 않고, LLM 대역이 호출되는 순간 래치를 내려 맞춘다. 그 시점이면 발화
저장이 끝나 커넥션을 이미 쥐고 있다.

### 결과

```
턴 처리 sessionId=44eb7cdd... 총 4076ms (저장 8ms, 분석 2048ms, 판단 0ms, 대사 2017ms)

로그인 소요 1013ms, 결과 CannotCreateTransactionException

HikariPool-1 - Connection is not available, request timed out after 1006ms
  (total=2, active=2, idle=0, waiting=0)
```

읽을 점 세 가지다.

- `active=2, idle=0` - 커넥션 두 개를 대화가 다 쥐고 있다
- 로그인은 `CannotCreateTransactionException`으로 끝났다. **쿼리를 던져보지도 못하고
  트랜잭션 시작 자체에서 실패했다.** 로그인이 무거워서가 아니라 순서를 못 받은 것이다
- 턴 4076밀리초 중 DB가 실제로 일한 시간은 30밀리초 남짓이다. 나머지는 LLM 대기다

## 3. 원인

### 트랜잭션이 곧 커넥션이다

`@Transactional` 메서드는 첫 DB 접근에서 풀의 커넥션 하나를 빌리고, 커밋하거나 롤백할
때까지 돌려주지 않는다. 그 사이 무엇을 하든 상관없다. DB를 쓰지 않고 외부 API 응답을
기다리기만 해도 커넥션은 계속 묶여 있다.

`TurnOrchestrator.processUtterance`가 `@Transactional`이고, 안에서 부르는
`analysisService.analyze`와 `messageService.append`는 전파 설정이 기본값(REQUIRED)이라
새 트랜잭션을 열지 않고 바깥 트랜잭션에 합류한다. **턴 하나가 트랜잭션 하나다.**

### 시간축

```
[커넥션 대여]
  |
  +- INSERT 아이 메시지            8ms    DB 사용
  +- 분석 LLM 호출              2048ms    DB 놀고 있음   <- 커넥션 쥔 채로
  +- INSERT 분석 결과, 누적 갱신     0ms    DB 사용
  +- 진행 판단                     0ms    순수 계산
  +- 캐릭터 LLM 호출            2000ms    DB 놀고 있음   <- 커넥션 쥔 채로
  +- INSERT 캐릭터 메시지, 세션 갱신 17ms    DB 사용
  |
[커밋, 커넥션 반납]              총 4076ms
```

점유 시간의 99% 이상을 아무 일도 하지 않으면서 붙들고 있다.

### 왜 다른 API까지 막히는가

커넥션 풀은 **앱 전체가 공유하는 자원**이다. 로그인도, 홈 조회도, 상점도 같은 풀을 쓴다.
대화가 풀을 다 가져가면 나머지는 대기열에 서고, Hikari 기본 대기 시간 30초를 넘기면
예외가 난다.

운영 기본값으로 계산하면 이렇다. 풀 10개, 턴 하나가 5초를 점유한다고 하면 동시에 처리
가능한 대화는 10건, 처리량은 초당 2턴이다. 열한 번째 아이가 말하는 순간부터 서비스 전체가
멈춘다.

### 상한이 없다는 점

여기에 `WebClientConfig`가 비어 있어 외부 호출에 타임아웃이 없었다. 벤더가 응답하지 않으면
위 그림의 2048밀리초 자리가 무한대가 된다. 커넥션은 영영 반납되지 않고, Postgres의
`idle_in_transaction_session_timeout`도 기본 미설정이라 서버가 끊어주지도 않는다.

한 번 막히면 재기동 말고는 풀리지 않는 상태였다.

## 4. 왜 이렇게 짜였나

의도적인 선택이었고, 그 선택에 나름의 근거가 있었다는 점을 적어 둔다.

턴 하나를 한 트랜잭션으로 묶으면 **중간에 무엇이 실패하든 없던 일이 된다.** 캐릭터 LLM이
실패했는데 아이 발화만 저장돼 있는 상태, 분석은 저장됐는데 세션 누적은 갱신되지 않은 상태
같은 것이 생기지 않는다. 대화 기록과 진행 상태가 어긋나면 복구가 까다로운 도메인이라
원자성을 우선한 것은 자연스럽다.

문제는 그 트랜잭션 안에 외부 호출이 들어 있다는 것이지 트랜잭션 자체가 아니다. 외부 호출은
DB 트랜잭션이 보장해 주는 것이 아무것도 없으면서 시간만 길다.

## 5. 적용한 것

### 5-1. 외부 호출 타임아웃 (완료)

`WebClientConfig`에 연결 3초, 응답 10초를 걸었다. `HTTP_CONNECT_TIMEOUT_MS`,
`HTTP_RESPONSE_TIMEOUT_MS`로 재배포 없이 조정할 수 있다.

재시도는 **연결 실패에만** 1회 건다. 응답 타임아웃은 재시도하지 않는다.

- 서버가 이미 요청을 받아 처리 중일 수 있어 같은 발화가 두 번 처리될 수 있다
- LLM은 호출당 과금이다
- 10초를 기다렸다 또 10초를 기다리면 아이는 마이크 앞에서 20초를 보낸다

연결 실패는 다르다. 서버에 닿지도 못했으므로 아무것도 보내지지 않았고, 다시 보내도 중복이
생기지 않는다.

주의할 점이 하나 있다. `responseTimeout`은 응답 전체의 마감이 아니라 **읽기와 읽기 사이의
최대 간격**이다. 한 번에 내려오는 JSON에서는 사실상 마감처럼 동작하지만, 스트리밍으로
바꾸면 조각이 계속 도착하는 한 시간 제한이 걸리지 않는다. 그때는 호출부에서 전체 시간을
따로 걸어야 한다.

본문 로깅은 넣지 않았다. 이 클라이언트가 실어 나르는 것은 아이 발화 원문과 벤더 API 키다.

### 5-2. 구간별 소요 시간 계측 (완료)

`TurnTimer`가 저장, 분석, 판단, 대사 네 구간을 재고 턴마다 한 줄을 남긴다.

```
턴 처리 sessionId=... 총 4076ms (저장 8ms, 분석 2048ms, 판단 0ms, 대사 2017ms)
```

실패해도 남긴다. 외부 호출이 타임아웃으로 끊겼을 때가 이 숫자를 가장 보고 싶은 순간이다.
발화 원문이나 캐릭터 대사는 담지 않는다. 시간을 보려고 남기는 로그에 대화 내용이 딸려
들어가면 그때부터 로그 보관 기간이 개인정보 문제가 된다.

### 5-3. 트랜잭션 경계 분리 (예정)

외부 호출을 트랜잭션 밖으로 뺀다.

```
[트랜잭션 1] 아이 메시지 저장                      -> 커밋
             분석 LLM 호출                          (트랜잭션 밖)
[트랜잭션 2] 분석 저장, 누적 갱신, 진행 판단 기록  -> 커밋
             캐릭터 LLM 호출                        (트랜잭션 밖)
[트랜잭션 3] 캐릭터 메시지 저장, 장면 이동         -> 커밋
```

커넥션 점유가 4076밀리초에서 30밀리초 수준으로 떨어진다. `backend-dev-guide.md`의 파이프라인
설계에 분석 단계가 "트랜잭션 밖"이라고 적힌 것도 이 구조를 전제한 것이다.

실제 작업량은 애노테이션을 떼는 데 있지 않다. 트랜잭션이 끝나면 `StorySession`이 detached가
되고, `open-in-view: false`라서 LAZY 연관에 접근하는 순간 예외가 난다. 지금 코드는 한
트랜잭션 안이라는 전제로 세션 객체를 계속 들고 다니므로, 각 구간이 세션을 다시 읽고 구간
사이에는 엔티티 대신 필요한 값만 넘기는 형태로 바꿔야 한다.

| 항목 | 전 | 후 |
| --- | --- | --- |
| 벤더 무응답 시 대기 | 무한 | 최대 10초 |
| 연결 실패 시 | 즉시 실패 | 1회 재시도 |
| 턴 하나 최악 소요 | 상한 없음 | 약 20초 (LLM 2회) |
| 막힌 뒤 복구 | 재기동 | 자동 |

| **커넥션 점유 시간** | **상한 없음** | **여전히 턴 전체** |

굵게 표시한 줄이 핵심이다. 지금까지 한 일은 "한 번 막히면 영영 안 풀리는" 상태를 없앤 것이지
커넥션을 붙들고 있는 구조를 고친 것이 아니다. 총 4076밀리초 중 30밀리초만 DB를 쓴다는 사실은
그대로다.

### 트랜잭션 분리 후 (예상)

| 항목 | 분리 전 | 분리 후 |
| --- | --- | --- |
| 커넥션 점유 시간 | 4076ms | 30ms 수준 |
| 동시 대화 중 로그인 | 실패 | 정상 |
| 풀 10개로 감당 가능한 동시 대화 | 10건 | 사실상 제한 없음 |
| 중간 실패 시 상태 | 전부 롤백 | 부분 커밋 (아래 참고) |

`TurnConnectionExhaustionTest`의 로그인 검증이 통과로 바뀌는지가 확인 기준이다. 지금은
고쳐야 할 동작을 적어 둔 채 `@Disabled`로 두었다.

## 7. 남은 것

### 트랜잭션 분리의 대가

원자성을 잃는다. 캐릭터 LLM이 실패하면 아이 발화와 분석은 커밋된 채 캐릭터 대사만 없는
상태가 남는다. 클라이언트가 그대로 재시도하면 같은 발화가 또 쌓이고 턴 카운트가 두 번 오른다.

복구 경로 자체는 있다. `GET /api/sessions/{sessionId}/turn-state`가 구현돼 있어 클라이언트가
현재 모드와 남은 요소를 다시 읽을 수 있다. 남은 것은 중복 방지이고, 방식이 두 가지다.

1. 요청에 멱등키를 받아 같은 키면 저장된 결과를 그대로 돌려준다
2. 아이 메시지에 처리 상태를 두고, 미완 메시지가 있으면 이어서 처리한다

프론트가 재시도를 어떻게 하는지에 따라 갈리므로 함께 정해야 한다.

### 커넥션 풀 설정

현재 `application.yml`에 설정이 없어 Hikari 기본값 10이 조용히 적용되고 있다. 트랜잭션을
분리하면 10으로 충분해지지만, 값을 명시하고 근거를 주석으로 남기는 편이 낫다. 대기 시간
기본값 30초도 너무 길다. 빨리 실패해야 원인이 보인다.

앱을 여러 인스턴스로 띄울 경우 풀 크기 곱하기 인스턴스 수가 Railway Postgres의 연결 상한을
넘지 않는지도 확인이 필요하다.

### 타임아웃 계층 정합성

LLM 10초를 두 번 부르니 최악 20초에 처리 시간이 붙는다. 바깥쪽 타임아웃(Railway 프록시,
프론트 HTTP 클라이언트)이 이보다 길어야 안쪽이 먼저 끊긴다. 바깥이 먼저 끊기면 서버는 계속
일하는데 클라이언트만 포기하는 상태가 된다.
