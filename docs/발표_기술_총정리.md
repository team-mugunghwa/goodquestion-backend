발표 자료의 근거 문서다. 세 저장소(서비스 백엔드, 프론트엔드, 관리자 백엔드)의 코드와
문서, perf 측정 결과에서 직접 확인한 사실만 적었다. 주요 문제 해결 사례는 마지막 장에
STAR(Situation, Task, Action, Result) 형식으로 정리했다.

수치 확인 기준일: 2026-08-18. 백엔드 develop, 프론트엔드 main, 관리자 백엔드 develop.

## 1. 시스템 구성

### 1.1 배포 토폴로지

```
사용자 앱 (Flutter Web, Vercel) ----+
                                    +--> 서비스 백엔드 (Spring Boot, Railway) --+
                                                                               +--> PostgreSQL (Railway, 공유 1대)
                                    +--> 관리자 백엔드 (Spring Boot, Railway) --+
관리자 콘솔 (Flutter Web, Vercel) --+
```

- 두 백엔드가 같은 PostgreSQL을 본다. 복제나 동기화 계층이 없어, 관리자가 공지/이야기/문의
  답변을 만지면 사용자 앱에 즉시 반영된다.
- Flyway 이력 테이블을 분리(`flyway_schema_history` / `flyway_schema_history_admin`)하고,
  공유 테이블 DDL은 양쪽에 `if not exists`로 중복 보유해 어느 쪽이 먼저 떠도 된다.
- 3D 행성은 React + three.js로 만든 별도 웹앱을 Flutter 배포에 정적으로 동봉해 같이 나간다.

## 2. 대화 엔진

### 2.1 역할 3분리: LLM을 쓰되, 판정은 맡기지 않는다

턴 하나에 관여하는 세 주체의 책임을 명시적으로 나눴다.

| 주체 | 하는 일 | 하지 않는 일 |
|---|---|---|
| 발화 분석 LLM | 아이 발화에서 사고 요소 8종 태깅 | 진행 여부 판단 |
| 진행 판단 규칙 엔진 (`ProgressionEngine`) | 계속 / 유도 / 종료 결정. LLM 미사용 순수 규칙 | 문장 생성 |
| 캐릭터 LLM | 캐릭터 성격을 유지한 대사 생성 | 장면 종료, 미션 판정 |

- 사고 요소 8종: DECISION, REASON, PERSPECTIVE, SOLUTION, RESULT, EMOTION, EMPATHY, REQUEST
- 발화 유효성 5종: VALID / SHORT / UNCLEAR / OFF_TOPIC / PLAYFUL. 각각 다른 유도 응답으로 이어진다.
- 진행 모드 3종: NORMAL / GUIDED / CLOSING. 종료 사유는 GOAL_MET(필수 요소 충족 + 최소
  대화량) 또는 MAX_TURNS(장면별 4~5턴 상한, 이때는 평가 없이 자연스럽게 다음 장면).
- 강한 유도(GUIDED)는 첫 발화, 새 요소를 확인한 턴, 직전이 GUIDED였던 턴에는 금지.
  무진전 2연속 / 저정보 2연속 / 남은 턴 2 이하 임계값은 환경변수로 조정 가능.
- 유도 방식: "해결 방법을 말해 봐" 같은 직접 질문을 금지하고, 캐릭터의 남은 걱정
  (remainingWorries)을 드러내는 간접 유도로 학습지 문항처럼 보이지 않게 했다.

### 2.2 LLM 출력 후처리: 걸러내기만 하고 보태지 않는다

분석 LLM의 출력을 서버가 4단계로 거른다.

1) 근거(evidence)가 발화 원문에 없는 요소 삭제 - 모델이 지어낸 근거 차단
2) 6자 미만이거나 막연한 SOLUTION 삭제
3) 중복 요소 제거
4) 스키마 밖 요소 제거

형식 자체는 OpenAI Structured Outputs(json_schema strict)로 공급자 수준에서 강제하고,
reasoning_effort는 minimal로 잡아 아이의 대기 시간을 줄였다. 감정 값이 정의된 6종을
벗어나면 NEUTRAL로 폴백한다.

### 2.3 화면 연출 계약

- phase(STORY / DIALOGUE / POST_ACTIVITY / ENDED)는 서버가 계산한 파생값이다. 프론트는
  장면 번호로 분기하지 않는다 - 화면 분기 로직이 서버와 어긋날 길을 애초에 막았다.
- 캐릭터 표정은 서버 분석 값(새로 충족된 사고 요소 diff)만으로 정하는 상태 머신.
  장면별 4~8개 상태, WebP 27장.
- 미션 2종(문제 해결형, 관점 전환형)은 대화 시작과 동시에 노출하지 않고 발화 흐름을
  확인한 뒤 노출한다 - 정답 찾기 게임이 되는 것을 방지.

## 3. 음성 기술

### 3.1 STT 신뢰도: 벤더가 안 주면 서버가 만든다

- 벤더(gpt-4o-mini-transcribe)는 신뢰도를 직접 주지 않는다. `include[]=logprobs`로 토큰
  로그 확률을 받아 서버가 exp(logprob 평균)으로 신뢰도를 직접 집계한다 (`OpenAiSttClient`).
- 기준값 0.5는 문헌 근거로 확정했다: Whisper 실패 컷 0.37과 품질 의심 0.6 사이에서,
  아동 낭독체 오인식률(성인 2% 미만 대비 26~40%)을 고려해 아동 쪽으로 완화한 값.
  환경변수로 빼서 배포 없이 조정할 수 있다.
- "모름(null)과 낮음(0)은 다르다" 원칙: 신뢰도를 못 받은 발화는 저신뢰로 취급하지 않는다.
- 저신뢰 발화는 다시 말하기 안내로 이어지고, 보호자 리포트의 대표 발화에서도 제외된다.

### 3.2 STT 환각 3겹 방어

무음이나 잡음이 들어오면 모델이 어휘 힌트 프롬프트를 그대로 복창하는 환각이 있었다
(복창의 신뢰도가 0.9 이상이라 저신뢰 컷으로는 못 잡는다는 것을 실측으로 확인).

1) 서버 에코 필터: 나열 에코 + 재조합 에코(힌트 등장 비율 2/3 이상) 판정 후 422
2) 문장형 프롬프트로 복창 유인 자체를 축소
3) 프론트 확인 단계 "이렇게 들었어요"로 아이가 제출 전에 직접 확인

여기에 근접 오인식 교정(자모 단위)과 영어 환각 필터를 추가했다. perf 측정에서 비발화
입력의 환각율이 100%에서 0%로 떨어졌고, 회귀 테스트 9건으로 고정했다.

### 3.3 녹음 파이프라인

- record 패키지 스트리밍 PCM을 WAV로 변환. 샘플레이트는 네이티브 16kHz, 웹은 브라우저
  협상값(48kHz)을 따른다 - 브라우저가 요청을 조용히 바꾸는 문제의 근본 대응 (13장 STAR 6).
- 녹음 상한 60초: 서버 멀티파트 한도(10MB) 대비 여유를 두고 프론트에서 먼저 자른다.
  30초 16kHz mono WAV가 약 960KB로 Boot 기본 한도 1MB에 걸리던 것을 10MB/12MB로 상향.
- 오디오 크기 초과는 413, 빈 텍스트는 422로 구분 응답.

### 3.4 TTS: 3벤더 라우팅과 2단 캐시

- OpenAI / Gemini 2.5 Flash TTS / Google Cloud Chirp 3 HD 3벤더를 매 합성마다
  `app_settings`(tts.vendor)로 라우팅한다. 관리자 콘솔에서 바꾸면 재배포 없이 즉시 적용.
  알 수 없는 값이면 조용한 폴백 대신 503 - "언제부터 어느 벤더였는지"가 흐려지는 것을 막는다.
- 캐시 1단: 장면 고정 대사는 `scene_audio` 테이블에 사전 렌더해 둔다. 대사 원문의
  `text_hash`를 함께 저장해, 대사가 수정되면 낡은 음성을 감지한다. 메타데이터 전량을
  기동 시 불변 맵으로 올려 장면 렌더마다 나가던 조회를 없앴다.
- 캐시 2단: 실시간 합성 결과 캐시. **라우터 위 데코레이터 한 벌**로 두고 키에 벤더를
  포함한다. 원래는 벤더 클라이언트 3개가 각자 같은 캐시를 들고 있었는데, 라우터가
  한 벌만 쓰므로 나머지 둘은 항상 비어 있었다 - 캐시는 벤더가 아니라 합성이라는
  행위의 관심사였다.
- 상한은 개수가 아니라 **바이트 예산**이다. 값이 base64 data URL이라 문장 길이에 따라
  37KB에서 176KB까지 벌어져, 개수로 상한을 두면 힙 점유가 예측되지 않는다.
- perf 실측: 캐시 미스 1.2~2.5초(문장 길이별), 캐시 적중 8.8~11.2ms.

### 3.5 캐릭터별 목소리와 화자 일관성 검증 (팀원 측정 자료)

- 며느리 / 시아버지 / 이장 / 내레이션 4화자를 구분해 합성한다. 대사마다 감정 6종을
  연출해 표정 상태 머신과 함께 몰입을 만든다.
- 화자 일관성을 실측으로 검증했다: 같은 문장을 사전 렌더와 실시간 합성 두 경로로
  만들어 기본주파수(F0)를 측정. 며느리 목소리는 213.4Hz vs 213.2Hz로 차이 0.14Hz -
  이 음역에서 사람이 구분하는 최소 차이(약 1Hz)의 1/7 아래라 아이 귀에는 같은
  목소리가 이어진다. 시아버지 / 이장은 5~14% 편차가 남아 벤더 전환으로 보완 중.
- 낭독 자막은 글자 수 추정이 아니라 합성 음성의 문장별 실측 타임스탬프로 동기화한다.

### 3.6 장면 영상 (팀원 제작 자료)

- 정지 삽화를 생성형 영상으로 만들었다: 7장면 8클립(1280x720). 인물 / 의상 / 배경이
  보존되는지 프레임 대조로 검수하고, 인물이 무너진 생성 컷은 탈락시켜 카메라 워크로
  대체했다.
- 대화 장면은 배경이 멈추고 캐릭터만 움직이는 10초 무이음 루프.
- 서버에는 장면 영상 스키마(V17__add_scene_video)가, 프론트에는 영상 재생과 실패 시
  삽화 폴백 경로가 있다. 영상 자산의 배포 반영 여부는 발표 직전 배포본에서 확인할 것 -
  반영 전이어도 삽화로 동일하게 동작한다.

## 4. 한국어 처리와 비용 엔지니어링

### 4.1 형태소 분석기 선정: 릴리스 이력을 실측하고 골랐다

- 후보 비교를 감이 아니라 데이터로 했다: KOMORAN 최종 릴리스 3.3.9(2020년 1월, 6년 전)
  vs Lucene Nori 10.4.0(2026년 2월, Apache Lucene 공식, mecab-ko-dic 표준 사전).
  Maven Central과 GitHub API로 2026-08-16 직접 확인 후 Nori를 채택했다.
- 과절단 안전장치: 떼어낸 꼬리가 조사/어미 품사일 때만 분석 결과를 신뢰한다.
  ("방빙끄"가 "방"으로 둔갑하는 오류 차단. 길이 규칙은 "감에서" 오차단 사례로 기각)

### 4.2 단어 저장 비용 계층: LLM 호출을 서비스 전체에서 단어당 최대 1회로

단어 저장 1건마다 LLM을 부르면 왕복 1~3초 + 토큰 비용이 들고, "기왓장이"와 "기왓장을"이
서로 다른 단어로 중복 생성된다. 이를 계층 필터로 풀었다.

| 계층 | 내용 | 상태 |
|---|---|---|
| 0 | Nori 표제어 정규화 - 조사/어미 제거로 같은 낱말 통합 | 구현 |
| 1 | 표제어 기준 중복 검사 - 이미 있으면 즉시 반환 | 구현 |
| 2 | 이야기 어휘 사전(story_vocabulary) - 고정 대사의 낱말은 검수된 뜻을 시드로 보유 | 구현 |
| 3 | 전역 캐시 - 다른 사용자가 이미 생성한 뜻 재사용 | 캐시 키 정책 결정 대기 |
| 4 | LLM 생성 - 위 계층을 모두 통과한 새 낱말만 | 구현 |

계층에 걸리면 응답이 1~3초에서 수십 ms로 줄어든다. 고정 대사의 낱말은 폐집합이라
미리 검수해 둘 수 있다는 관찰이 계층 2의 근거다.

### 4.3 단어 뜻 품질: 모델이 지킬 수 있는 규칙으로 바꾸기

- "20자 이내" 규칙을 모델이 계속 어겼다(11건 중 7건 초과). 원인은 모델이 글자 수를 세지
  못한다는 것 - 검증 불가능한 제약이었다.
- 기준을 어절(띄어쓰기 단위, 5~7어절)로 바꾸고 "정확함을 해치면서까지 줄이지 않는다"는
  우선순위 서열을 명시했다. 5~7어절은 초등 1학년이 한 호흡에 읽는 범위(분당 63어절)에서
  나온 수치다.
- 실재 낱말 판정(isRealWord)은 "애매하면 통과"로 못박았다 - 실재하는 말("아궁이")을
  거절하는 비용이 이상한 말을 통과시키는 비용보다 크다는 판단. 이 판정은 STT 오인식
  단어가 단어장(학습 기록)에 영구히 남는 경로를 422 INValID_WORD로 차단하는 관문이기도
  하다. 추가 LLM 왕복 없이 기존 호출에 판정 필드를 얹었다.
- 결과: 길이 초과 7/11 -> 1/11, 오거절 1건 -> 0건, 예문 3종 충족 0/33 -> 33/33 (5개 버전 측정).

### 4.4 예문 따라 말하기 판정: 결정적 채점

- 학습 콘텐츠 "예문 따라 말하기"의 90% 판정은 LLM이 아니라 결정적 알고리즘이다:
  글자/숫자만 남기는 정규화 후 Levenshtein 편집거리 기반 일치율 (`SentenceSimilarity`).
- 화면에 보여주는 퍼센트와 별가루 지급 판정이 같은 값을 쓴다(소수 둘째 자리 반올림 후
  0.90 비교) - "화면은 90%인데 보상이 안 나오는" 불일치를 구조적으로 차단.
- 단어 말하기 연습은 Nori 형태소 분석으로 조사/어미가 붙어도 인정하는 관대한 판정.

## 5. 인증 보안

### 5.1 로그인 브루트포스 방어: 지수 백오프 계정 잠금

- 비밀번호는 BCrypt 해시로만 저장한다.
- 실패 5회부터 잠금이 시작된다. 잠금 시간은 15분에서 시작해 실패가 누적될 때마다
  2배씩 늘고(지수 백오프), 최대 24시간에서 멈춘다. 시프트 연산 오버플로까지 방어 코드로
  막아 뒀다 (`Parent.recordLoginFailure`).
- 실패 기록은 REQUIRES_NEW 별도 트랜잭션으로 커밋한다 (`LoginAttemptService`). 인증
  실패를 예외로 알리는 구조에서 같은 트랜잭션에 두면, 롤백될 때 실패 횟수도 같이 사라져
  계정이 영영 잠기지 않는 구멍이 생긴다. 프록시 우회 문제(자기 호출 시 REQUIRES_NEW
  무시)까지 고려해 클래스를 분리했다.
- 잠금 중 로그인 시도는 423 응답. 로그인에 성공하면 실패 카운터와 잠금이 리셋된다.
- 관리자가 정지한 계정(blocked)은 잠금(lockedUntil)과 사유를 구분해 다룬다. 비밀번호가
  맞아도 정지 계정은 들어올 수 없고, 잠금보다 먼저 검사한다.

### 5.2 토큰 체계: 짧은 액세스, 회전하는 리프레시

- 액세스 토큰 30분 / 리프레시 토큰 14일.
- 리프레시 토큰은 1회용이다. 사용하면 즉시 폐기(revoke)하고 새로 발급한다(회전).
  폐기된 토큰의 재사용은 차단된다 - 토큰 탈취를 조기에 무력화한다.
- 리프레시 토큰 원문은 서버에 저장하지 않는다. 해시만 저장해 DB가 유출돼도 토큰을
  재사용할 수 없다 (`RefreshToken.tokenHash`, unique).
- 로그아웃 시 리프레시 토큰을 무효화한다. 401(인증 만료, 리프레시 유도)과 403(권한
  없음)을 구분해 응답한다.

### 5.3 계정 찾기: 편의 기능에도 보안 조건이 있다

- 이메일(ID) 찾기: 목적 자체가 이메일을 알려주는 것이라 계정 존재를 완전히 숨길 수는
  없다. 대신 본인 확인 강도를 입력 정보로 가른다 - 자녀 이름과 출생연도까지 맞히면 그
  자녀로 좁혀 찾고, 이름만으로 찾는 경로에서는 자녀가 하나라도 등록된 계정은 절대
  나오지 않는다. 아이가 있는 계정은 아이 정보 없이 못 찾게 하는 것이 핵심 보안 조건이다
  (`FindEmailService`).
- 비밀번호 재설정: 1회용 토큰, 유효 30분(설정값). 없는 토큰, 만료된 토큰, 이미 쓴 토큰을
  모두 구분해 거절한다. 메일 발송은 운영에서 Resend HTTP API를 쓴다(11장 참고).

### 5.4 소셜 로그인: 토큰 교환은 서버가 한다

- 카카오 / 구글 2종. 프론트는 시스템 브라우저(flutter_web_auth_2)로 인가 코드만 받고,
  authorization_code 교환은 서버가 직접 수행한다 - 소셜 액세스 토큰이 브라우저나 앱에
  남지 않는다.
- 발급된 JWT는 OS 보안 저장소(flutter_secure_storage)에 보관한다.
- 소셜 계정은 비밀번호가 없으므로 보호자 게이트 통과 정책을 서버 정책과 함께 별도로
  정의했다.

### 5.5 접근 통제

- 모든 아이/세션 리소스는 컨트롤러 진입 시 JWT의 보호자 ID(@CurrentParentId)로 소유권을
  검증한다. 남의 리소스 접근은 403.
- CORS 허용 목록에 Vercel 프리뷰 패턴을 넣을 때 팀 슬러그까지 포함했다
  (`goodquestion-frontend-*-team-mugunghwa.vercel.app`) - 같은 이름의 남의 프로젝트가
  허용되는 것을 차단.
- 관리자 백엔드는 JWT 서명 키를 서비스와 분리했다. 같은 키를 쓰면 보호자 토큰이 관리자
  API를 통과하는 구멍이 생긴다는 것을 문서에 명시하고 막았다. 관리자 리프레시 토큰은
  12시간 + 회전 + SHA-256 해시 저장, 로그인 5회 실패 시 15분 잠금.
- 프론트 보호자 게이트: 리포트/설정 영역 진입 시 비밀번호 확인. 영역 안에서는 재확인하지
  않고, 벗어나면 리셋된다 - 아이에게 태블릿을 넘겼을 때를 대비한 설계.

## 6. 개인정보 보호

- 원본 음성 비저장: 아이 음성은 STT 변환에만 쓰고 서버에 남기지 않는다. 텍스트만 저장.
- 아이 계정 무접속기록: 접속 기록은 보호자 계정에만 남긴다. 만 14세 미만 아동의
  개인정보 수집에 해당하지 않게 하는 설계.
- 접속 기록 최소화: `last_login_at` / `last_login_ip`는 이력 테이블이 아니라 마지막 1건
  덮어쓰기다. 관리자 화면이 묻는 것이 "마지막"뿐이고, 보관 개인정보를 최소화하며, 계정
  삭제 시 함께 소멸한다. 로그인 실패는 IP도 시각도 남기지 않는다 - 잠금이 목적이지
  실패한 사람 추적이 목적이 아니다.
- 방문 통계는 `daily_visits`에 날짜별 사람 수만 집계한다.
- LLM에 아이 이름을 보내지 않는다: 프롬프트에는 자리표시자를 쓰고 저장 직전에 서버가
  치환한다.
- 아동 동의 게이트: 동의 없이 세션 시작 불가(409 CONSENT_REQUIRED).
- 관리자 콘솔의 DB 탐색기는 읽기 전용 + 민감 컬럼 마스킹이며, 개인정보 테이블 열람
  자체가 감사 로그(READ_DATA)에 남는다. 관리자 엔티티는 화면이 쓰는 컬럼만 매핑해
  비밀번호 해시나 소셜 식별자가 응답에 실릴 길이 없다.

## 7. 데이터 정합성

### 7.1 동시 중복(겹침): 3중 락

- 세션 진행 상태는 낙관적 락(`StorySession.version`) - 연타로 겹친 갱신은 409.
- 발화 순번은 유니크 제약 unique(session_id, turn_order) - DB가 최종 방어선.
- 별가루 지갑은 비관적 락(SELECT FOR UPDATE) - 잔액 갱신 경합 차단.
- 지급 자체의 멱등성은 부분 유니크 인덱스로 보장 - 같은 사유의 중복 지급이 DB에서 막힌다.
- 이 충돌들은 전역 핸들러로 뭉개지 않고, 턴 의미가 성립하는 지점에서 409
  CONCURRENT_TURN으로 변환한다.

### 7.2 순차 중복(재시도): 멱등키

- 락으로는 못 막는다 - 타임아웃 후 재전송은 첫 트랜잭션이 이미 커밋된 뒤라 조정할
  대상이 없다. 재전송인지 새 작업인지는 클라이언트만 안다.
- Stripe / AWS 관행을 따라 `Idempotency-Key` HTTP 헤더 규약을 도입했다. UUID 키, 24시간
  보관, 완료된 요청의 재전송은 저장된 응답 재생, 처리 중이면 409 REQUEST_IN_PROGRESS.
- 저장소는 인메모리나 Redis가 아니라 DB 테이블(`idempotent_requests`) - 인스턴스가 늘어도
  동작이 같다. `INSERT ... ON CONFLICT DO NOTHING` 선점, 재생 시 소유권 검증까지
  PostgreSQL 특성에 맞춰 구현했다.
- **실패한 키를 지울지는 작업이 원자적인지에 달렸다.** 처음에는 무조건 지웠는데
  ("실패했으면 아무것도 커밋되지 않았다"는 전제), 발화 처리는 트랜잭션 셋으로 쪼개져
  있어 그 전제가 깨진다. 아이 발화가 커밋된 뒤 캐릭터 LLM이 실패했을 때 키를 지우면
  재시도가 발화를 한 번 더 저장한다 - **멱등키가 막겠다고 선언한 중복을 멱등키의
  실패 처리가 만들어 냈다.** 한 트랜잭션인 구매는 지금도 지우고, 발화는 FAILED로 남겨
  같은 키의 재시도에 409 REQUEST_ALREADY_FAILED를 준다.
- 상태 변경 엔드포인트 30여 개를 전수 조사한 뒤, 피해가 돈(별가루)인 두 곳(발화 제출,
  아이템 구매)부터 적용했다.

### 7.3 자연 멱등: 키가 필요 없는 곳은 상태로 푼다

- 멱등키는 클라이언트가 헤더를 챙겨야 동작한다. 서버 상태만으로 중복을 판별할 수 있는
  곳은 키 없이 푸는 것이 낫다.
- `story-complete`는 다 본 장면 id를 받아 현재 장면과 다르면 전진하지 않는다. 없을 때는
  재전송 한 번에 장면 하나를 통째로 건너뛰었는데, 화면은 정상으로 보이고 아이만
  그 대목을 못 본 채 이야기가 이어진다.
- 첫 대사 재생(`opening`)은 이미 같은 방식이었다 - 기존 메시지가 있으면 그것을 돌려준다.
- 세션 중단(`stop`)은 진행 중일 때만 멈춘다. 가드가 없을 때는 완주 직후 도착한 중단
  요청이 COMPLETED를 덮어 completedAt만 남는 모순 상태를 만들었다.

### 7.4 턴 트랜잭션 구조

- 발화 턴 1건 = 짧은 DB 트랜잭션 3구간 + 트랜잭션 밖 LLM 호출 2회. 구간 간 값 전달은
  record 5종으로 명시했다.
- 트랜잭션 분리로 원자성 일부를 포기하는 대가는 알고 지불했다: 캐릭터 LLM이 실패하면
  부분 커밋 상태가 남지만, turn-state 조회로 복구 경로를 제공한다.
- **이 대가가 멱등키 쪽으로 새어 나갔다는 것은 나중에 알았다**(7.2). 턴을 쪼갠 것도
  실패한 키를 지운 것도 각각은 근거 있는 결정이었는데, 둘이 만나는 지점을 아무도
  보지 않았다. 결정 하나하나가 옳아도 조합은 따로 검토해야 한다.

### 7.5 조회 쿼리 정리

- 세션 조회(`getOwnedSession`)는 대화, 후속 활동, 리포트가 함께 쓰는 공용 진입점인데
  세션 1회 + 소유권 검증이 보는 child 1회 + 호출자가 보는 currentScene 1회로 세 번이
  나갔다. 페치 조인으로 1회가 됐고, 턴당 9회가 3회가 된다(Hibernate 통계 실측).
- 응답 시간 이득은 10ms대로 미미하다. **이득은 지연이 아니라 커넥션에 있다** - 풀이
  10개라 동시 사용자가 늘면 여기가 먼저 막힌다. 이 판단은 8.3의 "풀은 처리량 손잡이가
  아니다"와 같은 맥락이다.
- 콘텐츠 마스터(scene_audio, topics, items)는 이 서버에 쓰기 경로가 없고 Flyway 시드로만
  바뀐다. 재배포가 곧 재적재라 **무효화 코드가 0줄**이다. 판단 기준과 캐시 종류 선택
  근거는 `docs/캐시_전략.md`에 있다.

## 8. 성능

### 8.1 재현 측정 하네스

- 버전마다 전용 git worktree + 전용 빈 PostgreSQL 17(해당 버전 마이그레이션/시드)을
  격리해 같은 입력으로 재측정한다. 벤더 LLM은 전 버전 동일 모델로 실호출.
- 트랙 5개: 이야기 완주 여정(4버전 x 3회, 12/12 성공), 턴 동시부하(k6 16VU, LLM은 2초
  고정 지연 스텁 대역), 단어 뜻 품질(33표본 x 5버전), STT 환각(15표본 x 5버전), TTS 캐시.

### 8.2 핵심 수치 (perf/results, 2026-08-17 로컬 재현 측정)

| 항목 | 전 | 후 |
|---|---|---|
| 턴 처리 중 DB 커넥션 점유 | 4,076ms | 55ms |
| 대화 부하 중 로그인 p95 | 3,528ms | 117.5ms |
| 대화 부하 중 홈 p95 | 3,467.75ms | 35ms |
| 같은 시나리오 완료 턴 수 | 216건 | 336건 (실패 0) |

| STT p95 | 1,541.2ms | 904.1ms |
| 단어 예문 3종 충족 | 0/33 | 33/33 |

### 8.3 런타임 설정

- 가상 스레드 활성(JDK 25): STT / LLM / TTS 대기 중 플랫폼 스레드를 점유하지 않는다.
- Hikari 풀 상한 10, 커넥션 대기 3초, 누수 감지 2초(정상 트랜잭션 55ms 대비 회귀 감지용).
  풀을 키우지 않은 근거도 문서화했다 - 턴당 커넥션 사용 합계 79ms, 풀 10개 기준 이론상
  초당 126턴. 풀은 처리량 손잡이가 아니다.
- 외부 호출 타임아웃 연결 3초 / 응답 10초, 재시도는 연결 실패에만 1회. 벤더 오류는
  502(AI_UPSTREAM_ERROR) / 429(AI_RATE_LIMITED) / 503(AI_UNAVAILABLE)으로 구분.
- 보호자 리포트는 세션 완료 커밋 후 비동기 생성(@Async + AFTER_COMMIT 이벤트). 리포트가
  늦어도 완주와 보상에는 영향이 없다. 완성 전 조회는 409 REPORT_NOT_READY.
- 비동기 스레드풀 core 2 / max 8 / queue 100. graceful shutdown 20초.

## 9. 프론트엔드

### 9.1 아키텍처

- feature-first 클린 아키텍처: 기능 모듈 9개, 각각 data(DTO) / domain(Entity) /
  presentation(ViewModel) 3계층. DTO와 Entity를 분리해 서버 계약 변경이 화면 코드에
  번지지 않는다.
- provider MVVM + get_it DI(등록 69건), go_router 라우트 23개, 전역 로그인 가드
  (토큰 없으면 /auth로, 로그인 상태로 /login 진입 시 홈으로).
- 화면별 더미 JSON을 백엔드 계약 초안으로 썼다 - 서버가 붙으면 DataSource만 교체하고
  화면 코드는 무변경 (ADR 015).

### 9.2 연출과 상태 관리

- 캐릭터 음성과 자막 동기화: 벽시계 타이머가 아니라 오디오 재생 위치 스트림(onPosition)에
  자막 시계를 묶었다 - 일시정지/재개가 자동으로 맞는다.
- 우주 배경 애니메이션은 패키지 없이 CustomPainter 직접 구현(713줄): 달의 8자 부유,
  별 24~64개 반짝임, 10초 루프에 유성 6줄기. 달은 정적 레이어로 캐시해 Transform으로만
  움직이고(재페인트 없음), 별 레이어는 화면 상단 55%로 제한, repaint 리스너블로 rebuild
  없이 페인트만 갱신한다. 기기의 동작 줄이기 설정이면 정지 프레임으로 대체.
- 에셋 최적화: 캐릭터 PNG 39MB -> WebP 3.4MB, 리캡 PNG 11MB -> WebP 400KB,
  가로 표지 PNG 2.5MB -> WebP 240KB.

### 9.3 3D 행성 통합

- React + three.js 웹앱을 같은 도메인 iframe(HtmlElementView)으로 심고, postMessage 채널
  규약(exit / error / ready / balance)으로 경계를 정의했다.
- 신원(보호자 토큰 + childId)은 postMessage가 아니라 iframe 쿼리 파라미터로 전달 - 렌더
  전에 도착해야 하는 값이라 메시지 경합을 설계로 제거했다.
- 캐릭터 걷기: 탭한 칸까지 점유 칸을 피해 경로를 탐색하고, walk 애니메이션 전환과 카메라
  추적까지 구현했다. 길이 없으면 "거기까지 갈 길이 없어요" 안내.
- WebGL 생성 실패 시 아이 눈높이 안내 화면으로 폴백, 오프라인이면 "모아 둔 건
  그대로예요" 표시. 두 손가락 확대로 못 돌아오는 문제를 막으려 pinch-zoom도 차단했다.

## 11. 배포와 운영

### 11.1 잘못된 설정으로는 아예 뜨지 않게 (3중 게이트)

1) 프론트 빌드 게이트(`tool/vercel_build.sh`): API_BASE_URL이 https가 아니면 빌드 중단

   최대 3회), graceful shutdown 20초 - push가 곧 배포인 구조에서 처리 중 요청을 지킨다.

### 11.2 파이프라인과 스키마

- push 자동 배포(Railway / Vercel) + CI(develop PR / push에서 gradlew test).

## 13. STAR 사례 모음

### STAR 1. 턴 처리 커넥션 점유

- **S (Situation)**: 동시 대화 2건만으로 로그인 등 무관한 API까지 실패했다 (재현: 풀 2,
  로그인 1,013ms 후 CannotCreateTransactionException).
- **T (Task)**: 대화가 몰려도 다른 기능이 느려지지 않게 격리한다.
- **A (Action)**: 구간별 계측(TurnTimer)으로 원인을 특정했다 - 트랜잭션 하나에 LLM 호출
  2회가 들어 있어 점유 4,076ms 중 DB 실사용은 30ms 남짓. 트랜잭션 경계를 3구간으로
  분리해 LLM 호출을 밖으로 빼고, 외부 호출 타임아웃(연결 3초 / 응답 10초)과 커넥션 풀
  명시 설정(10개, 대기 3초, 누수 감지 2초)을 더했다. 겹친 발화는 409로 변환.
- **R (Result)**: 커넥션 점유 4,076ms -> 55ms (74배). 부하 중 로그인 p95 3,528ms ->
  117.5ms, 홈 p95 3,467.75ms -> 35ms. 같은 시나리오 완료 턴 216 -> 336건(실패 0). 턴
  자체 소요는 유지 - "느림이 옮지 않게 됐다"가 핵심. 회귀 테스트 2종으로 고정.

### STAR 2. STT 어휘 힌트 에코 환각

- **S**: 아이 말풍선에 어휘 힌트 목록("며느리, 시아버지, 방귀, ...")이 그대로 표시되고
  발화로 저장까지 되는 일이 발생했다.
- **T**: 아이가 하지 않은 말이 화면과 DB에 도달하는 경로를 차단한다.
- **A**: 원인을 3겹으로 분해했다 - 1) 웹 녹음 샘플레이트 불일치(48kHz 데이터에 16kHz
  헤더), 2) 알아들을 수 없는 오디오에서 모델이 프롬프트를 복창하는 환각(신뢰도 0.9
  이상이라 저신뢰 컷 무력), 3) 프론트가 STT 결과를 무검증 즉시 제출. 각각 샘플레이트
  분기, 서버 에코 필터(나열 + 재조합, 힌트 등장 비율 2/3 기준), 아이 확인 단계
  "이렇게 들었어요"로 대응했다. 무음 / 잡음 재현 실측표까지 만들어 검증했다.
- **R**: 비발화 입력 환각율 100% -> 0% (perf 5버전 측정). 회귀 테스트 9건. "신뢰도는
  환각을 못 잡는다. 저신뢰 컷과 에코 필터는 별개의 방어다"라는 교훈을 문서로 남겼다.

### STAR 3. STT 신뢰도 산출

- **S**: 저신뢰 발화를 거르는 파이프라인의 양끝(DB 컬럼, 응답 플래그, 리포트 필터)만
  있고 가운데가 비어 있었다 - 벤더가 신뢰도를 주지 않아 항상 null이었다.
- **T**: 벤더 없이 신뢰도를 산출하고 판정 기준을 확정한다.
- **A**: `include[]=logprobs`로 토큰 로그 확률을 받아 서버가 exp(평균)으로 집계.
  기준값 0.5는 Whisper 실패 컷 0.37과 품질 의심 0.6 사이에서 아동 오인식률(26~40%)을
  고려해 완화한 값으로 확정하고, 단일 판정 창구(`SttConfidencePolicy`)와 "모름(null) !=
  낮음(0)" 원칙을 세웠다. 기준값은 환경변수로 분리.
- **R**: 왕복 스모크에서 신뢰도 0.999 수신. 경계 테스트(0.499 / 0.5 / null) 3종 고정.
  저신뢰 발화가 다시 말하기 안내와 리포트 제외로 이어지는 전 구간이 동작한다.

### STAR 4. 타임아웃 재전송 중복 처리

- **S**: 턴 처리 최악 20초 vs 모바일 기본 타임아웃이 그 언저리 - 정상 범위의 재전송이
  발화 중복 턴과 별가루 이중 차감을 만들 수 있었다.
- **T**: 재전송을 새 작업과 구분해 정확히 한 번만 처리한다.
- **A**: 동시 중복은 이미 3중 락으로 막혀 있었지만 순차 중복은 락으로 못 막는다는 것을
  정리하고(첫 트랜잭션이 이미 커밋됨), Stripe / AWS 관행의 Idempotency-Key 헤더 규약을
  도입했다. 저장소는 DB 테이블, ON CONFLICT DO NOTHING 선점, 24시간 보관, 처리 중 409.
  상태 변경 엔드포인트 30여 개를 전수 조사해 피해가 돈인 두 곳부터 적용.
- **R**: 재전송은 저장된 응답 재생으로 중복 0건. 통합 테스트 7건 고정.

### STAR 4-1. 그 멱등키가 스스로 만든 중복 (후속)

- **S**: STAR 4로 재전송 중복을 막았는데, 그 구현 안에 같은 중복을 만드는 경로가
  남아 있었다. 실패한 작업의 키를 지우는 처리가 "실패했으면 아무것도 커밋되지 않았다"를
  전제하는데, 턴은 커넥션 점유를 줄이려고 트랜잭션 셋으로 쪼개져 있어(STAR 1) 그
  전제가 성립하지 않는다. 아이 발화가 커밋된 뒤 캐릭터 LLM이 실패하면 키만 사라지고,
  같은 키의 재시도가 발화를 한 번 더 저장한다.
- **T**: 재실행이 안전한 작업과 위험한 작업을 갈라, 위험한 쪽은 재실행하지 않는다.
- **A**: 엔드포인트마다 재실행 가능 여부를 선언하게 했다. 한 트랜잭션인 구매는 지금처럼
  키를 지우고, 발화는 FAILED로 남겨 409 REQUEST_ALREADY_FAILED를 준다. 클라이언트는
  turn-state로 상태를 확인하고 새 턴이 필요하면 새 키로 보낸다. 서버가 어느 구간에서
  실패했는지 모르므로 보수적으로 전부 남기는 쪽을 택했고, 대가(새 키 발급 한 번)를
  문서에 남겼다.
- **R**: 부분 커밋 후 재시도의 중복 턴이 사라졌다. 기존 실패 테스트가 **안전한 경로만**
  덮고 있었다는 것도 함께 드러났다 - 분석 단계 실패는 아직 커밋 전이라 안전한데,
  위험한 경로(커밋 후 대사 실패)는 테스트가 없었다. **테스트가 있다는 사실이 오히려
  안심시킨 경우**다. 지금은 양쪽을 각각 고정한다.
- **말할 거리**: 두 결정이 각각은 옳았는데 조합에서 문제가 났다는 것. 좋은 설계
  결정끼리도 경계에서 충돌할 수 있고, 그 경계는 아무도 리뷰하지 않는다.

### STAR 5. 단어 뜻 생성 품질

- **S**: 실서버 측정에서 생성된 뜻의 64%(7/11)가 20자 규칙을 어기고, 실재 낱말
  "아궁이"를 거절하는 오거절도 있었다.
- **T**: 8살이 한 호흡에 읽을 수 있는 정확한 뜻을 안정적으로 생성한다.
- **A**: 실패 원인을 "모델은 글자 수를 못 센다(검증 불가능한 제약)"로 규정하고, 기준을
  어절(5~7어절)로 교체 + "정확함을 해치면서까지 줄이지 않는다" 서열 명시 + 오거절은
  "애매하면 통과"로 못박았다. 버전마다 33표본 재측정으로 효과를 확인했다.
- **R**: 길이 초과 7/11 -> 1/11, 오거절 0건, 예문 3종 충족 0/33 -> 33/33, 정확도 손실
  사례(부뚜막) 회복. 회귀 테스트 3건.

### STAR 6. 웹 녹음 샘플레이트 불일치

- **S**: 웹에서 녹음한 음성을 서버가 3배 느린 소리로 해석했다 (2.97초 녹음이 8.91초로).
- **T**: 브라우저 환경에서도 정확한 녹음 데이터를 만든다.
- **A**: 원인은 브라우저가 16kHz 요청을 조용히 48kHz로 바꾸는데 WAV 헤더는 16kHz로
  적은 것. 요청값이 아니라 브라우저 협상값을 따라 헤더를 쓰도록 고쳤다
  (`_sampleRate = kIsWeb ? 48000 : 16000`).
- **R**: 웹 녹음 정상화. 에코 환각의 3대 원인 중 하나가 제거됐다. 협상값이 48kHz가 아닌
  하드웨어의 재발 가능성은 한계로 문서에 남겼다.

### STAR 7. 첫 턴 우수 아이 보너스 역전 버그 (협업)

- **S**: 콘텐츠 확정안과 서버 시드 / 코드를 프론트가 전수 대조하다가, 첫 턴에 4요소를
  전부 채운 잘한 아이가 미션 노출 기회를 얻지 못해 장면 보너스를 못 받는 역전 구조를
  발견했다.
- **T**: 잘한 아이가 손해 보지 않게 미션 노출 / 보상 로직을 고친다.
- **A**: 프론트 담당자가 재현 경로, 원인 코드 위치, 수정안(A안)까지 문서로 만들어
  백엔드에 전달했고, 변경이 불필요한 항목도 부록으로 함께 검증했다.
- **R**: 수정 반영. "역할 경계를 넘는 전수 대조"가 팀의 협업 방식으로 남았다
  (BACKEND_REQUESTS 문서 4건).

### STAR 8. 메일 발송 포트 차단 (운영)

- **S**: 운영 환경(Railway)이 SMTP 587 포트를 막아 비밀번호 재설정 메일이 나가지 않았다.
- **T**: 운영에서 안정적으로 메일을 보낸다.
- **A**: SMTP 대신 Resend HTTP API(443)로 전환했다. 헬스체크에서 메일 인디케이터를
  의도적으로 제외해, 메일 벤더 장애가 서비스 헬스체크를 물고 내려가지 않게 했다.
- **R**: 운영 메일 발송 정상화. 외부 의존이 코어 가용성을 흔들지 않는 구조.

## 14. 발표에서 과장하면 안 되는 것

- LLM 장애 시 "고정 대사로 대화를 잇는" 폴백은 미구현이다 (안정성 목록 상태 "필요").
  타임아웃 + 502 / 503 구분 + 비동기 리포트 격리까지만 말할 것.
- 완전 플레이 가능한 이야기는 1편(9장면, 캐릭터 3, 미션 2). 목록의 6편은 카드만 있다.
- 홈의 추천 영역은 창업팀 스스로 "추천 로직 미구현, 영역만 배치"라고 명시했다.
- perf 수치는 로컬 재현 측정이다. 운영 수치로 말하지 말 것. 턴 동시부하 트랙의 턴
  p95는 LLM 스텁 대역 기준이다.
- STT 기준값 0.5는 문헌 근거 출발값이고 아동 실녹음 검증은 미완이다.
- 멱등키는 발화 제출과 아이템 구매 2곳 적용이다. "모든 API가 멱등"이 아니다.
  story-complete와 opening, stop은 키가 아니라 자연 멱등(서버 상태 판별)이다.
  story-complete의 장면 id는 **선택 파라미터**라, 구버전 클라이언트가 안 실으면
  지금도 무조건 전진한다. "중복 호출이 완전히 막혔다"가 아니라 "클라이언트가 실으면
  막힌다"까지가 사실이다.
- 캐시 작업의 이득은 **쿼리 수와 커넥션**이지 응답 시간이 아니다. 턴은 LLM 대기가
  96%라 줄인 DB 왕복은 10ms대다. 동시 처리량이 늘었다는 것은 논리적 추론이고
  부하 테스트로 재지 않았다 - 실측한 것은 쿼리 수(세션 조회 3 -> 1)뿐이다.
- TTS 2단 캐시의 적중률은 사전 렌더가 붙으면서 낮아졌다. 고정 대사는 이제 정적 파일로
  나가므로 이 캐시에 남는 것은 LLM 생성 대사(재사용 거의 없음)와 이름 치환 대사뿐이다.
  perf의 캐시 적중 수치는 그 이전 측정이다.
- 단어 음성 듣기는 기기 내장 TTS 임시 구현이다. 캐릭터 목소리가 아니다.
- 위험 발화 안전 신호 처리(safety), 레이트 리밋, 계정 탈퇴 경로는 미구현으로 남아 있다.
- 3D 모델은 Kenney 오픈 에셋이다. "3D 씬 구성과 인터랙션, 서버 연동을 자체 구현"으로
  표현할 것.
- 동의 철회는 세션 시작 차단까지 구현됐다. 기존 기록 조회 차단은 미완.
