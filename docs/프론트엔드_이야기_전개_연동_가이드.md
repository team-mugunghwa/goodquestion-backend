# 프론트엔드 이야기 전개 연동 가이드

이야기 시작부터 완료까지의 API 호출 순서와 장면 전환 기준.
1부는 구현하며 바로 따라가는 요약이고, 배경 설명은 2부에 있다.
요청/응답 필드 상세는 [API_및_DTO_명세.md](API_및_DTO_명세.md)가 원본이다.

# 1부. 빠른 참조

## 전체 흐름

```
세션 시작
  POST /api/children/{childId}/sessions        { storyId }
  -> sessionId 저장, phase 확인

[phase = STORY]  내레이션 장면
  1) scene의 내레이션 재생 (음성 필요 시 POST /api/tts { text })
  2) 재생 끝나면
     POST /api/sessions/{sessionId}/scenes/current/story-complete
  3) 응답의 phase로 분기
     STORY         -> 1)로 (다음 내레이션)
     DIALOGUE      -> openingMessage 재생 후 대화 루프로
     POST_ACTIVITY -> 후속 활동으로

[phase = DIALOGUE]  대화 장면 (턴 루프)
  1) 캐릭터 대사 재생 종료 -> 마이크 활성화
  2) 녹음 -> POST /api/stt (multipart, 파트명 audio) -> text
  3) 텍스트 표시, 아이가 확인 -> 보내기 (버튼 잠금)
     POST /api/sessions/{sessionId}/utterances
       { text, sttRawText?, sttConfidence?, sttRetryCount?, missionId? }
  4) 응답 분기 (아래 "발화 응답 분기" 표)
     계속       -> characterMessage 재생 후 1)로
     미션 노출  -> characterMessage 재생 + 미션 오버레이
     장면 종료  -> characterMessage(마지막 대사) 재생 후 전환

[장면 종료: sceneTransition 수신]
  next = SCENE
    -> GET /api/sessions/{sessionId}/scenes/current 로 새 장면 로드
    -> nextSceneType이 STORY면 내레이션으로, DIALOGUE면 opening 재생 후 대화로
  next = POST_ACTIVITY
    -> 후속 활동으로

[phase = POST_ACTIVITY]  후속 활동
  POST /api/sessions/{sessionId}/post-activity/start      -> 카드 (섞인 순서)
  POST /api/sessions/{sessionId}/post-activity/order      -> 오답이면 재시도, 정답이면 keywords
  (음성 재구성: /api/stt로 텍스트 확보)
  POST /api/sessions/{sessionId}/post-activity/retelling  -> 세션 완료, 별가루 지급

완료 후: 완료 화면 -> 내 행성 -> 보호자 인계(리포트)
```

## 발화 응답 분기 (`POST /utterances` 응답)

null 여부만 보면 된다. 순서대로 검사한다.

| 검사 | 의미 | 동작 |
|---|---|---|
| `sceneTransition != null` | 장면 종료 | `characterMessage`(고정 마지막 대사) 재생 -> 전환 |
| `mission != null` | 미션 노출 | `characterMessage` 재생 + 미션 오버레이 |
| 둘 다 null | 대화 계속 | `characterMessage` 재생 -> 다음 턴 |

## 장면 전환 기준 (누가 정하나)

| 상황 | 기준 | 주도 |
|---|---|---|
| STORY -> 다음 | 재생이 끝나면 `story-complete` 호출 | 프론트 |
| DIALOGUE -> 다음 | 응답에 `sceneTransition`이 실려 옴 | 서버 |
| 미션 노출 시점 | 응답에 `mission`이 실려 옴 | 서버 |
| 후속 활동 -> 완료 | `retelling` 제출 시 서버가 완료 처리 | 서버 |

프론트가 스스로 판단하는 것은 "재생이 끝났는가"뿐이다.
목표 달성, 유도, 미션 노출, 장면 종료는 전부 서버가 정한다.

## 미션

- 오버레이는 `mission != null`이 온 턴에만 띄운다
- 미션 수행 발화는 별도 API가 아니라 **다음 `utterances`에 `missionId`를 실어 보낸다**
- `POST /missions/{missionId}/result`는 아직 501 - 쓰지 않는다
- 새로고침 복구: `GET /api/sessions/{sessionId}/missions/current` (미노출이면 null - 정상)

## TTS 사용 기준

- 캐릭터 메시지의 `audioUrl`이 null이면 `POST /api/tts { text, characterName }` 호출
- 내레이션은 `characterName` 없이 호출 (내레이션 보이스)
- 응답의 `audioUrl`은 현재 data URL(base64 mp3)이다. 그대로 오디오 소스로 재생 가능

## 에러 대응

| 코드 | 상황 | 동작 |
|---|---|---|
| 409 `CONCURRENT_TURN` | 발화가 겹침 | **재전송 전에 `GET /turn-state`로 상태를 다시 읽는다** |
| 409 `MAX_TURNS_EXCEEDED` | 닫힌 장면에 재전송 | 상태를 다시 읽으면 장면이 이미 넘어가 있다 |
| 409 `SCENE_NOT_DIALOGUE` | STORY 장면에서 발화 전송 | 화면 상태 버그 - phase 확인 |
| 422 `STT_EMPTY_TEXT` | 인식 실패 | 메시지 미생성. 다시 말하기 안내 |
| 응답 타임아웃 | 서버는 처리를 마쳤을 수 있다 | 재시도 전에 `turn-state` 확인 |

## 복구

| 상황 | API |
|---|---|
| 이어하기, 새로고침 | `GET /api/sessions/{sessionId}/resume` - 장면 + 대화 내역 + 마지막 캐릭터 대사 + 노출 중 미션 |
| 턴 상태만 | `GET /api/sessions/{sessionId}/turn-state` |
| 첫 대사 재요청 | `POST /api/sessions/{sessionId}/scenes/current/opening` (멱등) |
| 중단 | `POST /api/sessions/{sessionId}/stop` |

## 주의

- **전송 중 보내기 버튼을 잠근다.** 턴 처리는 LLM 2회로 실측 약 6초, 최악 20초다.
  로딩 연출을 두고, HTTP 클라이언트 타임아웃은 25초 이상으로 잡는다
- 오디오 업로드 한도는 10MB (30초 WAV 여유 있음)
- `analysis`(의도/요소)는 캐릭터 표정/태도 연출의 트리거다. 프론트가 발화 내용으로
  자체 판단하지 않는다 (마음-01)
- `safety`는 항상 null (감지 미구현). 값이 생기는 시점은 별도 공지

# 2부. 배경 설명

## 왜 전환 주도권이 갈리나

STORY 장면은 정적 콘텐츠 재생이라 "언제 끝났는지"를 서버가 알 수 없다. 재생 완료는
프론트만 아는 사실이므로 프론트가 `story-complete`로 알린다.

DIALOGUE 장면의 종료는 "필수 사고 요소를 다 채웠는가 + 최소 대화량을 넘었는가" 또는
"최대 턴에 닿았는가"로 정해진다. 이 판정은 발화 분석과 누적 상태를 보는 서버 규칙
엔진의 몫이고, 프론트에는 판정 재료(요소 충족 현황)가 완전하게 주어지지 않는다.
`progress.missingElements`가 내려가긴 하지만 표시용이지 판정용이 아니다.

## 발화 한 건이 처리되는 동안 서버에서 일어나는 일

저장 -> 분석 LLM -> 후처리 -> 진행 판단(NORMAL/GUIDED/CLOSING) -> 미션 노출 판단 ->
캐릭터 LLM(또는 고정 마지막 대사) -> 저장. LLM 두 번이 순차라 수 초가 걸린다.
이 전체가 한 응답으로 돌아오므로 프론트는 중간 상태를 폴링할 필요가 없다.

## CONCURRENT_TURN에서 상태를 다시 읽으라는 이유

서버는 발화 저장과 캐릭터 응답을 별도 트랜잭션으로 처리한다. 겹친 요청 중 진 쪽이
아이 발화만 남기고 끝나는 경우가 있어, 그대로 재전송하면 같은 발화가 두 번 쌓일 수
있다. `turn-state`나 `resume`으로 현재 상태를 확인한 뒤 이어가는 것이 안전하다.
멱등키 도입이 논의 중이며, 도입되면 이 절차가 단순해진다.

## 마지막 대사와 다음 장면 첫 대사의 관계

장면이 닫히는 턴의 `characterMessage`는 콘텐츠에 고정된 마지막 대사다(평가가 아니라
다음 전개로 잇는 이야기 연결 대사). 서버는 이 응답을 주는 시점에 이미 다음 장면으로
옮겨 둔 상태고, 다음이 DIALOGUE면 첫 대사도 저장돼 있다. 프론트는 마지막 대사 재생을
마친 뒤 `scenes/current`로 새 장면을 그리고, DIALOGUE면 `opening`(멱등)으로 첫 대사를
받아 재생하면 순서가 맞는다.

## 고정 첫 대사의 이름 치환

"ㅇㅇ아," 같은 자리표시자는 서버가 아이 이름으로 치환해 내려준다. 프론트는 받은
텍스트를 그대로 표시/재생하면 된다.

## closingReason 활용

`GOAL_MET`(목표 달성)과 `MAX_TURNS`(최대 대화량 도달)를 구분해 연출을 다르게 할 수
있다. 단 어느 쪽이든 아이에게 성공/실패나 평가처럼 보여주지 않는다. MAX_TURNS도
이야기는 자연스럽게 다음으로 이어진다.

## 방귀 뀌는 며느리 기준 장면 순서 (참고)

```
1 도입(STORY) -> 2 전개1(STORY) -> 3 대화1(며느리, 최대 4턴)
-> 4 전개2(STORY) -> 5 대화2(시아버지, 최대 5턴)
-> 6 전개3(STORY) -> 7 대화3(이장, 최대 5턴, 미션1)
-> 8 전개4(STORY) -> 9 대화4(며느리, 최대 4턴, 미션2)
-> 후속 활동 -> 완료
```

순서는 참고일 뿐, 코드에서 장면 번호로 분기하지 않는다. `phase`와 `sceneType`으로만
분기해야 콘텐츠가 바뀌어도 프론트가 깨지지 않는다.
